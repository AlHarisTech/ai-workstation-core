# ADR-0004 — Execution Observability Layer

**Status:** PROPOSED
**Depends on:** ADR-0003-A (Execution Semantics), ADR-0003-B (Runtime Engine), ADR-0003-C (Agent Adapters), ADR-0003-D (Tool Adapters), ADR-0003-E (Governance Engine)
**Layer:** Cross-Cutting — Observability, Audit, Replay
**Scope:** All execution modes. Mode 0/1 have reduced observability surface.

---

## 1. Core Thesis

```
The Observability Layer is a passive, cross-cutting infrastructure
that captures the complete execution lineage (trace, state, inputs,
outputs, decisions) of every unit in the system without affecting
determinism or execution ordering.

It unifies three concerns that are currently separate:
  - Execution Journal (per-execution event log, ADR-0003-B §4.6)
  - Governance Audit (control-plane decisions, ADR-0003-E §4.7)
  - Execution Traces (per-node input/output/state lineage — NEW)

The layer enables:
  - Deterministic replay
  - Time-travel debugging
  - Cross-execution audit
  - Root cause analysis
  - Compliance reporting
  - State lineage for snapshot/rollback
```

---

## 2. Why Observability Now

The layers built so far create a complete execution substrate:

```
Compiler → RIR → CEG → Scheduler → Dispatcher → Agents/Tools → Commit
```

Every transition is deterministic. Every decision is bounded. Every failure has defined semantics.

**But the system cannot answer:**

```
"Why did this execution produce this result?"
"What was the exact input to agent X at step 3?"
"Which tool failed first in this wave?"
"What was the governance decision that rejected this admission?"
"Can I replay this execution bit-for-bit from the audit trail?"
```

Without observability, the system is a black box. With it, the system becomes debuggable, auditable, and verifiable.

**Critical boundary — Non-Interference Clause:**

```
Observability MUST NOT perform causal inference.
It only records and indexes raw events, relationships,
and state transitions.

All interpretation — root cause analysis, anomaly detection,
failure correlation — is delegated to external query layers
(analysis tools, dashboards, compliance systems).

Observability records WHAT happened.
It never determines WHY it happened.
```

This is a hardening of OB-001. The layer enriches by linking (e.g., attaching
governance decision refs to runtime traces), but it never enriches by
interpreting (e.g., "this admission rejection caused this node failure").

│      │              │             │               │          │
│      └──────────────┼─────────────┼───────────────┘          │
│                     │             │                          │
│                ┌────▼─────────────▼─────┐                    │

│                └────────────────────────┘                    │

         │                  │                  │
         ▼                  ▼                  ▼
    ┌─────────┐      ┌───────────┐      ┌───────────┐

The Observability Layer sits **alongside** all data-plane and control-plane components. It observes passively. It never participates in execution decisions. It never blocks, delays, or modifies any execution path.

| # | Component | Responsibility |

## 5. Trace Model

### 5.1 Execution Trace Schema

A trace is the complete record of a single execution unit (CEG node) from dispatch to commit.

```yaml
trace:
  # Identity
  trace_id: "<uuid>"
  execution_id: "<uuid>"
  node_id: "<uuid>"
  node_type: "agent" | "capability" | "task" | "gate" | "checkpoint"

  # Timing
  span:
    scheduled_at: "<iso8601>"
    dispatched_at: "<iso8601>"
    started_at: "<iso8601>"
    completed_at: "<iso8601>"
    committed_at: "<iso8601>"
    duration_ms: <int>

  # Context (what was the system state when this node ran)
  context:
    wave_id: <int>
    lane_id: <int>
    region_id: "<uuid>" | null
    execution_mode: "2" | "3"

  # Input (complete — enables replay)
  inputs:
    spec_ref: "<ref>" | null
    rir_hash: "<sha256>"
    ceg_hash: "<sha256>"
    contract_ref: "<contract-ref>"
    tool_allowlist: ["<tool-id>"] | null
    capability_contract_hash: "<sha256>" | null
    invocation_context: {}              # exact inputs passed to the unit

  # Execution (what happened)
  execution:
    provider: "<provider-id>" | null
    model: "<model-id>" | null
    sandbox_model: "<model>"
    tool_invocations:                   # for agents
      - tool_id: "<uuid>"
        inputs_hash: "<sha256>"
        result_hash: "<sha256>"
        status: "success" | "failure"
        duration_ms: <int>
    agent_state_snapshot: {} | null     # for agents (plan, history, variables)

  # Output (complete — enables verification)
  outputs:
    status: "success" | "failure" | "timeout" | "cancelled" | "sandbox_violation"
    result_hash: "<sha256>"
    artifacts: ["<ref>"]
    evidence: ["<ref>"]
    metrics:
      duration_ms: <int>
      tokens_used: <int> | null
      tools_invoked: <int>
      replans: <int>

  # Lineage (where did the data come from)
  lineage:
    predecessor_nodes: ["<node-id>"]
    predecessor_traces: ["<trace-id>"]
    handoff_from: "<trace-id>" | null
    data_flow:
      - from_node: "<node-id>"
        from_output: "<key>"
        to_input: "<key>"

  # Commit
  commit:
    sequence: <uint64>
    terminal_status: "SUCCESS" | "FAILURE" | "SKIPPED" | "TERMINATED"
    committed_at: "<iso8601>"
```

### 5.2 Trace Collection Protocol

```
For every node execution:

  1. Before dispatch:    RECORD trace.scheduled_at, trace.context, trace.inputs
  2. On dispatch:        RECORD trace.dispatched_at
  3. On execution start: RECORD trace.started_at
  4. During execution:   ACCUMULATE tool invocations, state snapshots
  5. On completion:      RECORD trace.completed_at, trace.outputs
  6. On commit:          RECORD trace.committed_at, trace.commit
  7. On journal write:   APPEND complete trace to Unified Event Store
```

**Critical rule:** Trace collection is ASYNCHRONOUS. The trace is assembled in memory during execution and flushed to the store after commit. Trace collection never adds latency to the execution path.

### 5.3 Trace Completeness Guarantee

```
A trace is COMPLETE when it contains:

  ✓ All inputs (sufficient for deterministic replay)
  ✓ All outputs
  ✓ All intermediate tool invocations (for agents)
  ✓ Complete timing span
  ✓ Full data lineage

A trace is INCOMPLETE when the node was TERMINATED mid-execution
or the runtime ABORTED. Incomplete traces are still stored but
marked incomplete: true.
```

## 6. Replay Engine

### 6.1 Purpose

```
Given an execution_id and a set of complete traces,
reconstruct the exact execution — same outputs,
same state transitions, same commit order.
```

### 6.2 Replay Protocol

```
REPLAY(execution_id):
  1. LOAD all traces for this execution from Unified Event Store
  2. VALIDATE: all traces are complete (or mark replayed execution as partial)
  3. SORT traces by commit.sequence
  4. For each trace in order:
     a. Load trace.inputs (exact inputs that were used)
     b. Execute the unit with those inputs
     c. Compare trace.outputs with replayed outputs
     d. If mismatch → REPLAY_DIVERGENCE (record, continue or abort)
  5. Return ReplayResult with divergence report
```

### 6.3 Replay Determinism Contract

```
REPLAY is deterministic if and only if:

  1. Same RIR (same rir_hash)
  2. Same compiler version
  3. Same plugin versions (agent/tool adapters)
  4. Same provider configurations
  5. ALL external providers satisfy one of:
     a) deterministic-mode locked (e.g., LLM temperature=0, seed fixed)
     b) snapshot-replayed (provider outputs served from recorded traces)
     c) explicitly mocked via trace inputs (no live provider call)

If any of these differ, REPLAY_DIVERGENCE is expected and
the replay is marked as NON_DETERMINISTIC.
```

**Why constraint (5) is required:**

Without it, replay may be syntactically correct but semantically divergent.
External systems (HTTP APIs, LLM providers with non-zero temperature,
MCP servers with time-dependent state, filesystems with external mutations)
introduce non-determinism that the Runtime Engine cannot control.
The Observability Layer MUST declare that replay fidelity depends on
external determinism — it cannot guarantee it unilaterally.

### 6.4 Replay Modes

| Mode | Description | Use Case |
|------|-------------|----------|
| `verify` | Re-execute and compare outputs — fail on divergence | CI/CD validation, compliance check |
| `observe` | Re-execute and record divergences without failing | Debugging, investigation |
| `fast_forward` | Skip re-execution, replay commit events from journal only | Quick timeline reconstruction |
| `time_travel` | Replay to a specific trace and stop | Debug a specific failure point |

## 7. Audit Engine

### 7.1 Purpose

Unify the Runtime Journal (ADR-0003-B §4.6) and Governance Audit (ADR-0003-E §4.7) into a single queryable surface. The Audit Engine does not replace these — it provides a cross-referenced view over both.

### 7.2 Audit Query Model

```yaml
audit_query:
  execution_id: "<uuid>" | null           # scope to one execution
  time_range:
    from: "<iso8601>"
    to: "<iso8601>"
  node_id: "<uuid>" | null                # scope to one node
  event_types: ["<event-type>"]
  status_filter: ["SUCCESS", "FAILURE"]
  governance_decision: "<verdict>" | null
```

### 7.3 Unified Audit Entry

```yaml
unified_audit_entry:
  sequence: <uint64>                      # global across runtime + governance
  source: "RUNTIME" | "GOVERNANCE"
  trace_id: "<uuid>" | null               # links to execution trace
  event: <Event>                          # original event from source stream
  governance_context:                     # only for RUNTIME entries
    admission_decision_id: "<uuid>" | null
    policy_manifest_hash: "<sha256>" | null
    capability_contract_hash: "<sha256>" | null
  execution_context:                      # only for GOVERNANCE entries
    node_id: "<uuid>" | null
    node_status: "<status>" | null
    triggered_by_trace: "<trace-id>" | null
```

### 7.4 Audit Queries (Examples)

```
"Show me every governance decision that affected execution X"
"Which nodes failed in the last wave of execution Y?"
"What tools did agent Z invoke and what were their results?"
"Which policy rejected this admission?"
"Show the full execution path that led to node A's FAILURE"
```

## 8. Lineage Engine

### 8.1 Purpose

Track the provenance of every piece of data that flows through the system. Answer: "Where did this output come from?"

### 8.2 Lineage Graph

```
Agent A (reads fs:/spec/prd.md)
    │
    ├──► tool: fs/read ──► outputs: { content: "..." }
    │
    ▼
Agent A (generates plan)
    │
    ├──► tool: llm/chat ──► outputs: { plan: [...] }
    │
    ▼
Agent B (receives plan via handoff)
    │
    ├──► tool: fs/write ──► outputs: { path: "/src/foo.rs" }
    │
    ▼
Agent C (reads generated file)
    │
    ├──► tool: fs/read ──► inputs: { path: "/src/foo.rs" }
    │                        lineage: { from: Agent B, tool: fs/write }
```

### 8.3 Lineage Entry

```yaml
lineage_entry:
  source:
    node_id: "<uuid>"
    trace_id: "<uuid>"
    output_key: "<key>"
    artifact_ref: "<ref>"
  target:
    node_id: "<uuid>"
    trace_id: "<uuid>"
    input_key: "<key>"
  relation: "DATA_FLOW" | "HANDOFF" | "ARTIFACT"
  provenance:
    rir_hash: "<sha256>"
    spec_ref: "<ref>"
```

## 9. Unified Event Store

### 9.1 Purpose

Single append-only durable store for all observability data: traces, audit entries, lineage records.

### 9.2 Store Schema

```yaml
store:
  # Partitioned by execution_id
  partitions:
    - execution_id: "<uuid>"

  # Streams within a partition
  streams:
    traces:
      - <Trace>
    audit:
      - <UnifiedAuditEntry>
    lineage:
      - <LineageEntry>
    snapshots:
      - <SnapshotReference>         # pointers to snapshot files

  # Global index (cross-execution)
  indices:
    by_time: "<iso8601>" → [entry_ref]
    by_node: "<node-id>" → [trace_ref]
    by_execution: "<execution-id>" → partition
    by_status: "<status>" → [trace_ref]
```

### 9.3 Storage Properties

```
- Append-only: no modification, no deletion
- Durable: writes survive process restart
- Compressible: traces can be compacted after execution completes
- Queryable: indices enable fast lookups
- Partitionable: each execution is an independent partition
- Retention: configurable per execution mode (Mode 3 = longer retention)
```

### 9.4 Ordering Semantics

```
The Unified Event Store guarantees:

  - TOTAL order within a single execution_id
    (consistent with Commit Engine sequence numbers and
     Governance sequence numbers)

  - PARTIAL order across execution_ids
    (no cross-execution ordering guarantee — events from
     different executions are not causally ordered)

  - NO global ordering guarantee
    (no single monotonically increasing global sequence)

Rationale:
  - Prevents false causality across executions
  - Eliminates replay confusion in multi-execution analysis
  - Avoids global sequence contention
  - Consistent with per-execution sequence scoping (GI-017)
```

## 10. Integration Contracts

### 10.1 Observability ↔ Runtime Engine

```
Runtime publishes:  NodeCommitted, NodeFailed, NodeTerminated events
Observability consumes: Events via the Event Bus (read-only)
Observability enriches: Events with trace data, appends to Unified Event Store

Observability NEVER:
  - Writes to the Runtime Event Bus
  - Modifies node state
  - Blocks or delays event delivery
```

### 10.2 Observability ↔ Governance Engine

```
Governance publishes:  PolicyDecisions, AdmissionDecisions, EscalationSignals
Observability consumes: Governance Event Stream (read-only, via Signal Adapter)
Observability enriches: Governance entries with execution context linkage

Observability NEVER:
  - Modifies governance decisions
  - Publishes to the Governance Event Stream
  - Influences policy evaluation
```

### 10.3 Observability ↔ Agent/Tool Adapters

```
Adapters produce:  Execution traces (per invocation)
Observability collects: Trace data during execution
Observability stores: Complete trace after commit

Observability NEVER:
  - Modifies adapter inputs or outputs
  - Intercepts tool invocations
  - Affects execution timing
```

### 10.4 Observability ↔ Commit Engine

```
Commit Engine:     Commits node state, publishes NodeCommitted
Observability:     Completes trace, appends to store AFTER commit

Observability NEVER:
  - Participates in the commit protocol
  - Validates or rejects commits
  - Delays commit publication
```

## 11. Performance Constraints

| Constraint | Value | Rationale |
|-----------|-------|-----------|
| Trace assembly latency | < 1ms per trace | Must not impact execution throughput |
| Store append latency | < 5ms per entry | Async flush, not in execution path |
| Store query latency (indexed) | < 50ms | Audit queries must be responsive |
| Store size per execution | < 100MB (Mode 2), < 1GB (Mode 3) | Mode 3 traces include agent state snapshots |
| Replay overhead vs original | < 110% duration | Replay should not be significantly slower |

## 12. Invariants

| ID | Invariant | Enforced By |
|----|-----------|-------------|
| OB-001 | Observability is passive — it never affects execution decisions; it records WHAT happened, never determines WHY (causal inference is delegated to external layers) | All observability components |
| OB-002 | Trace collection is asynchronous — it never adds latency to the execution path | Trace Collector |
| OB-003 | Trace completeness is verified — incomplete traces are marked explicitly | Trace Collector |
| OB-004 | Replay with identical inputs, RIR, compiler, plugins, and providers produces identical outputs | Replay Engine |
| OB-005 | Audit entries are immutable once stored | Unified Event Store |
| OB-006 | Lineage tracks every data flow edge in the CEG | Lineage Engine |
| OB-007 | Unified Event Store is append-only — no modification, no deletion | Unified Event Store |
| OB-008 | Observability components never write to Runtime Event Bus or Governance Event Stream | All observability components |
| OB-009 | Observability data is partitioned by execution_id — cross-execution queries are possible but scoped | Unified Event Store |
| OB-010 | Trace retention policy is configurable per execution mode | Unified Event Store |

## 13. Replay Scenarios

### 13.1 CI Validation

```
Scenario: After a compiler or plugin update, verify that a known-good
execution produces identical results.

  1. Load execution traces from known-good run
  2. Replay in `verify` mode
  3. Assert zero divergences
  4. If divergence → block deployment
```

### 13.2 Debugging a Failure

```
Scenario: A node in wave 3 failed. Why?

  1. Query audit: show all events in execution X, wave 3
  2. Identify failed node and its trace
  3. Replay in `time_travel` mode, stopping at failed node
  4. Inspect inputs, context, tool invocations
  5. Replay in `observe` mode to see divergence point
```

### 13.3 Compliance Audit

```
Scenario: Prove that policy set P was in effect during execution X.

  1. Query audit: show governance decisions for execution X
  2. Extract policy_manifest_hash from admission decision
  3. Compare with known policy set hash
  4. Lineage shows all nodes governed by this policy
```

## 15. Decision Outcome

The Observability Layer is a passive, cross-cutting infrastructure that captures complete execution lineage (traces, audit, lineage) without affecting determinism or execution performance. It unifies Runtime Journal and Governance Audit into a single queryable surface. The Replay Engine enables deterministic reconstruction of any prior execution, bounded by external provider determinism constraints (providers must be deterministic-mode locked, snapshot-replayed, or mocked). The Lineage Engine tracks data provenance across all nodes and handoffs. All observability data is stored in an append-only, partitioned Unified Event Store with total order per execution and partial order across executions. Observability components never write to execution event buses, never participate in execution decisions, and never perform causal inference — interpretation is delegated to external analysis layers.

---

## 16. Consequences

**Positive:**
- Complete execution visibility — every input, output, decision, and transition is recorded
- Deterministic replay enables CI validation, debugging, and compliance verification
- Unified audit surface eliminates the need to correlate separate Runtime and Governance logs
- Lineage enables root cause analysis across multi-agent workflows
- Passive design ensures zero performance impact on execution
- Enables future features: wave rollback, state recovery verification, anomaly detection

**Constraints:**
- Storage cost scales with execution complexity (traces + agent state snapshots)
- Replay requires matching RIR, compiler, plugin, provider versions, AND external provider determinism (temperature=0, fixed seed, snapshot-replayed, or mocked)
- Trace collection adds memory overhead during execution (traces held until commit)
- Cross-execution queries are limited to partial order — no global causal chain across executions
- Incomplete traces (TERMINATED, ABORTED) cannot be fully replayed
- Observability records but never interprets — root cause analysis requires external tools

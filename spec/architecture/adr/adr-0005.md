# ADR-0005 — Execution State Model (Snapshot / Recovery / Rollback)

**Status:** PROPOSED
**Depends on:** ADR-0003-B (Runtime Engine §4.7 Snapshot Engine), ADR-0003-A (Execution Semantics), ADR-0004 (Observability Layer)
**Layer:** Runtime Core — State Persistence & Recovery
**Scope:** Mode 3 only. Mode 2 has no persistence.

---

## 1. Core Thesis

```
The Execution State Model transforms the rich observability substrate
(full traces, full state, full lineage — ADR-0004) into a minimal
recovery representation that enables deterministic resume without
storing complete execution history.

A Snapshot is NOT a compressed trace.
A Snapshot is the minimum state required to RESUME execution.
A Trace is the full record required to REPLAY execution.
They serve different purposes but share lineage provenance.

The model provides three capabilities:
  1. Snapshot — persist minimal resume state at a checkpoint
  2. Recovery — resume execution from a snapshot
  3. Rollback — revert to a prior wave boundary within an active execution
```

---

## 2. State Compression Strategy

### 2.1 The Core Problem

ADR-0004 captures everything. A full agent trace may contain:

```yaml
trace_size_estimate:
  agent_state:              50KB - 2MB     (plan + history + variables)
  tool_invocations:         10KB each      (inputs + outputs + metrics)
  full_node_context:        20KB - 200KB   (contract + allowlist + RIR refs)
  lineage_graph:            O(n²) per wave (dense dependency edges)
```

For a Mode 3 execution with 100 nodes, 50 waves, and 5 agents:
**Raw trace storage: 50MB - 500MB per execution.**

A snapshot cannot store all of this. It must store the minimal subset.

### 2.2 Compression Principle

```
A Snapshot stores:

  ✓ WHAT is needed to resume execution
  ✗ NOT everything that happened during execution
```

### 2.3 What Goes Into a Snapshot

| Data | In Snapshot? | Rationale |
|------|-------------|-----------|
| Node status map (all nodes) | ✓ FULL | Required to know which nodes are terminal |
| Scheduler state (current lane, wave) | ✓ FULL | Required to know where to resume |
| Coordinator state (runtime_state, signal_origin) | ✓ FULL | Required for lifecycle continuity |
| Agent state for INFLIGHT agents | ✓ FULL | Required to resume mid-agent execution |
| Agent state for COMPLETED agents | ✗ SUMMARY | Only outputs + artifacts, not full plan history |
| Tool results for completed tools | ✗ SUMMARY | Only status + output refs, not full inputs |
| Full tool invocation history | ✗ OMIT | Reconstructible from traces if needed |
| Lineage graph | ✗ OMIT | Reconstructible from CEG + node status map |
| Event Bus events | ✗ OMIT | Re-derivable from Commit Engine on replay |
| Trace data (ADR-0004) | ✗ REFERENCE | Pointer to trace ID, not trace content |

### 2.4 Agent State Compression

An agent's state is the largest variable component. The compression rule:

```text
Agent state IN SNAPSHOT:
  - Plan: current step index + remaining steps + their status
  - Context: accumulated outputs (keys only), artifact refs, evidence refs
  - Variables: all (scoped, bounded size)
  - Tool invocation log: SUMMARY only (tool_id + status + summary string)

Agent state NOT IN SNAPSHOT:
  - Full plan history (initial plan, all replan iterations)
  - Full tool inputs/outputs (these are in traces)
  - replan_history details (reason strings)
```

### 2.5 Scheduler State Compression

```text
Scheduler state IN SNAPSHOT:
  - current_layer, current_wave
  - completed_nodes (id list)
  - ready_queue (id list)
  - blocked_nodes (id list)

Scheduler state NOT IN SNAPSHOT:
  - Wave partition details (recomputable from CEG + status map)
  - Lane assignments (recomputable from topological order)
  - Conflict matrix (recomputable from side_effect_surface)
```

## 3. Snapshot Schema (Refined from ADR-0003-B §4.7)

```yaml
snapshot:
  snapshot_id: "<uuid>"
  created_at: "<iso8601>"
  execution_plan_hash: "<sha256>"
  rir_hash: "<sha256>"
  compiler_version: "<semver>"
  execution_mode: "3"
  schema_version: "1.0"

  # Runtime fingerprint (CRITICAL — ensures recovery/replay consistency)
  runtime_fingerprint:
    plugin_versions:
      "<plugin-id>": "<semver>"
    adapter_versions:
      "<adapter-id>": "<semver>"
    scheduler_version: "<semver>"

  # Minimal node status map (all nodes, compressed)
  status_map:
    - node_id: "<uuid>"
      status: "SUCCESS" | "FAILURE" | "SKIPPED" | "TERMINATED"
      outputs:
        refs: ["<ref>"]               # references only, not full content
      artifacts: ["<ref>"]
      evidence: ["<ref>"]

  # Agent state (only for agents not yet terminal)
  agent_state:
    - agent_node_id: "<uuid>"
      plan:
        current_step: <int>
        remaining_steps: ["<step-id>"]
        step_status: { "<step-id>": "pending" | "running" }
      context_summary:
        accumulated_keys: ["<key>"]
        artifact_refs: ["<ref>"]
      variables: {}
      tool_log_summary:
        - tool_id: "<uuid>"
          status: "success" | "failure"
          count: <int>

  # Scheduler cursor
  scheduler_cursor:
    current_layer: <int>
    current_wave: <int>
    completed_nodes: ["<uuid>"]
    ready_queue: ["<uuid>"]
    blocked_nodes: ["<uuid>"]

  # Coordinator state
  coordinator_state:
    runtime_state: "RUNNING"
    signal_origin: "<node-id>" | null

  # Trace provenance (link to full observability data, not embedded)
  trace_ref:
    execution_id: "<uuid>"
    last_trace_id: "<uuid>"           # last trace recorded before snapshot

  # Context for agent continuity
  context_snapshot:
    session_refs: ["<ref>"]
    memory_refs: ["<ref>"]
    artifact_refs: ["<ref>"]
    variables: {}
```

## 4. Recovery Engine

### 4.1 Recovery Protocol

```
RECOVER(snapshot_id):
  1. LOAD snapshot from durable storage
  2. VALIDATE (any mismatch = SNAPSHOT_INCOMPATIBLE):
     - snapshot.execution_plan_hash == current_execution_plan.hash
     - snapshot.rir_hash == current_rir_hash
     - snapshot.compiler_version == current_compiler_version
     - snapshot.runtime_fingerprint matches current runtime
     - snapshot.execution_mode == current_execution_mode
     - snapshot.schema_version is compatible
  3. RESTORE status_map → set all node states
  4. RESTORE agent_state → for each inflight agent:
     - Rebuild plan from remaining_steps + current_step
     - Restore context_summary (keys and refs only)
     - Restore variables
  5. RESTORE scheduler_cursor → rebuild lane/wave position
  6. REBUILD wave partition from CEG + status_map + scheduler_cursor
  7. RESUME execution from next wave
```

### 4.2 What Recovery Does NOT Do

```
Recovery NEVER:
  - Replays tool invocations (RI-018)
  - Re-derives agent state (RI-014)
  - Recomputes completed waves
  - Replays events from the Event Bus
  - Loads full trace data (uses summary only)
  - Calls Governance during recovery (admission was already granted)
```

### 4.3 Recovery State Rebuilding

The scheduler cursor stores **position**, not **structure**. On recovery:

```
REBUILD_WAVE_PARTITION(CEG, status_map, scheduler_cursor):
  1. Load CEG (immutable, from RIR)
  2. Load status_map (restored from snapshot)
  3. Identify current layer = scheduler_cursor.current_layer
  4. For current layer:
     - Identify remaining nodes (status ∈ {PENDING, BLOCKED, READY})
     - Rebuild wave partition using conflict rules (ADR-0003-A §5)
     - Skip waves already completed (all nodes terminal)
     - Position at scheduler_cursor.current_wave
  5. Return ready_to_resume = true
```

The wave partition is **recomputable** from CEG + status_map + side_effect_surface. The snapshot stores the cursor position, not the partition itself.

**Deterministic rebuild constraint (SS-012):**

```
The REBUILD_WAVE_PARTITION algorithm MUST produce identical output
given identical (CEG, status_map, scheduler_cursor).

To guarantee this:
  - Remaining nodes are sorted by deterministic total order:
    sort(remaining_nodes, tie_breaker = sha256(node_id + rir_hash)[0:16])
  - Conflict resolution (graph coloring) uses the same node ordering
  - No randomization, no wall-clock-time-dependent behavior
  - No concurrency within the rebuild step itself
```

## 5. Rollback Engine

### 5.1 Purpose

```
Rollback reverts execution to a prior wave boundary within
the same execution. It is NOT recovery from a persisted snapshot.
It is an in-memory state rewind to a prior consistent point.

Rollback is used when:
  - A wave produced results that fail validation
  - An agent's replan exhausted and the parent orchestrator
    decides to retry the wave with modified context
  - A governance signal requires re-execution of a wave
```

### 5.2 Rollback Protocol

```
ROLLBACK(execution_id, target_wave_id):
  1. VALIDATE: target_wave_id < current_wave_id
  2. LOAD pre-wave snapshot (automatically captured before each wave)
  3. RESTORE status_map to pre-wave state
  4. RESTORE agent states for agents active in target wave
  5. EMIT ROLLBACK_MARKER overlay event to Unified Event Store:
     - marker.wave_id = target_wave_id
     - marker.affected_trace_ids = [traces from rolled-back waves]
     - marker.rollback_count = current_rollback_count + 1
     (Traces remain immutable — overlay preserves OB-005, ADR-0004 §13)
  6. RESUME execution from target wave

Constraint:
  - Rollback is bounded to a single execution instance
  - Rolled-back traces are preserved (marked rolled_back, not deleted)
  - Rollback count is limited (max 3 per wave, configurable)
```

### 5.3 Pre-Wave Snapshot

Before every wave executes, the Runtime Engine automatically captures a minimal pre-wave snapshot in memory:

```yaml
pre_wave_snapshot:
  wave_id: <int>
  captured_at: "<iso8601>"
  status_map_snapshot: {}              # node states before wave
  agent_states_snapshot: {}            # agent states before wave
  scheduler_cursor_snapshot: {}        # position before wave
```

This is lightweight — it captures only the delta state from the prior wave's completion. It lives in memory during execution and is discarded when the execution completes (or persisted if Mode 3 checkpoint).

### 5.4 Rollback Constraints

| Rule | Description |
|------|-------------|
| RB-001 | Rollback always goes to a wave boundary — never mid-wave |
| RB-002 | Max 3 rollbacks per wave (prevents infinite retry loops) |
| RB-003 | Rollback does NOT mutate traces. A `ROLLBACK_MARKER` overlay event is appended to the Unified Event Store referencing affected trace IDs. Traces remain immutable (OB-005). |
| RB-004 | Rollback does NOT replay governance admission (already admitted) |
| RB-005 | Cross-execution rollback is FORBIDDEN (immutable once execution completes) |
| RB-006 | Rollback resets the Scheduler's wave cursor — the CEG is never mutated |

## 6. Integration with Observability Layer

### 6.1 Trace → Snapshot Relationship

```
For every checkpoint snapshot:
  1. Snapshot stores trace_ref.last_trace_id
  2. This links the snapshot to the last committed trace
  3. Full trace data for all completed nodes is in the Unified Event Store
  4. Snapshot only stores what's needed for RESUME
  5. Traces store everything needed for REPLAY
```

### 6.2 Verifying Recovery Correctness

```
VERIFY_RECOVERY(execution_id, snapshot_id):
  1. Load snapshot
  2. Recover execution (RESUME)
  3. After execution completes, load full trace set from ADR-0004
  4. Compare:
     - Did the recovered execution produce the same outputs
       for already-completed nodes? (should be identical — no re-execution)
     - Did the recovered execution produce deterministic results
       for remaining nodes? (should match if replay conditions hold)
  5. If mismatch → RECOVERY_DIVERGENCE (audit event)
```

### 6.3 Rollback Trace Integrity

```
When a wave is rolled back:
  1. A ROLLBACK_MARKER overlay event is appended to the Unified Event Store
  2. The marker references all trace_ids from the rolled-back wave onward
  3. Traces themselves are NEVER modified (OB-005 — immutable)
  4. New traces are recorded for the re-executed wave
  5. Both original and re-executed traces are preserved
  6. Audit query reconstructs execution history by:
     - Reading traces in sequence order
     - Skipping traces referenced by ROLLBACK_MARKER events
     - Reading re-executed traces that follow the marker
```

## 7. Invariants

| ID | Invariant | Enforced By |
|----|-----------|-------------|
| SS-001 | Snapshot stores minimum resume state — not full execution history | Snapshot Engine |
| SS-002 | Recovery never replays tool invocations or agent executions | Recovery Engine (RI-018) |
| SS-003 | Recovery never re-derives scheduler state — it loads exact cursor | Recovery Engine (RI-014) |
| SS-004 | Snapshot restore requires full hash AND runtime fingerprint compatibility (execution_plan, RIR, compiler, runtime_fingerprint, mode, schema) | Recovery Engine |
| SS-005 | Rollback is bounded — max 3 per wave | Rollback Engine |
| SS-006 | Rolled-back traces are preserved, not deleted | Rollback Engine + Observability |
| SS-007 | Snapshot compression never loses information required for deterministic resume | Snapshot Engine |
| SS-008 | Pre-wave snapshots are captured automatically before every wave in Mode 3 | Runtime Engine |
| SS-009 | Cross-execution rollback is forbidden — each execution is an immutable unit | Rollback Engine |
| SS-010 | Rollback resets cursor only — CEG is never mutated | Rollback Engine (RI-001) |
| SS-011 | Snapshot is a MATERIALIZED DERIVATION of (CEG + committed traces + scheduler state), NOT an independent source of truth — the traces and CEG are authoritative | Snapshot Engine |
| SS-012 | Scheduler rebuild on recovery MUST use deterministic total order: `sort(remaining_nodes, tie_breaker = node_id + rir_hash)` — no non-deterministic ordering | Recovery Engine |

## 8. Snapshot Lifecycle

```
ACTIVE EXECUTION (Mode 3)
       │
       │ checkpoint node reached in CEG
       ▼
SNAPSHOT CREATED
       │
       ├── Compress agent states (summary only)
       ├── Capture scheduler cursor
       ├── Capture coordinator state
       ├── Link to last trace (trace_ref)
       ├── Persist to durable storage
       │
       ▼
EXECUTION CONTINUES
       │
       │ execution terminates (success/failure/terminated)
       ▼
SNAPSHOT RETAINED (for recovery)
       │
       │ recovery or re-execution requested
       ▼
SNAPSHOT LOADED → RECOVERY → RESUME
       │
       │ execution completes successfully
       ▼
SNAPSHOT ARCHIVED (optional — for audit)
```

## 9. Recovery Scenarios

### 9.1 Clean Recovery

```
Scenario: Mode 3 execution was TERMINATED (MODE_INSUFFICIENT, F-004).
Router reclassifies, creates new execution with same RIR.

  1. Load last snapshot from prior execution
  2. Validate hash compatibility
  3. Restore status_map, agent_states, scheduler_cursor
  4. Resume from next wave
  5. All completed nodes remain SUCCESS — no re-execution
```

### 9.2 Partial Recovery (Agent Crash)

```
Scenario: An agent in wave 5 crashed (plugin failure).
The coordinator issued ABORT. The journal has all commits up to wave 4.

  1. Load pre-wave-5 snapshot
  2. Rollback to wave 5 boundary
  3. Re-execute wave 5 with recovered agent state
  4. Continue normally
```

### 9.3 Deterministic Verification

```
Scenario: After recovering from snapshot, verify that the recovered
execution matches the original (for compliance).

  1. Recover from snapshot → complete execution
  2. Load original traces from ADR-0004 (for waves that were already completed)
  3. Compare: completed node outputs in recovered execution
     MUST match original traces (no re-execution = identical)
  4. Compare: post-recovery waves produce deterministic results
     (if replay conditions hold from ADR-0004 §6.3)
```

## 11. Decision Outcome

The Execution State Model defines snapshot as a minimal resume representation (not full trace), derived from CEG + committed traces + scheduler state (SS-011), recovery as exact state restoration with full runtime fingerprint validation (SS-004), and rollback as bounded wave-level state rewind using overlay markers that preserve trace immutability (RB-003). Agent states are compressed to summaries for completed agents and full state only for inflight agents. Scheduler state is stored as a cursor position; wave partitions are rebuilt deterministically on recovery using a total-order tie-breaker (SS-012). Pre-wave snapshots enable bounded rollback within an execution. Trace provenance links snapshots to full observability data without embedding it. All snapshots are immutable once created.

---

## 12. Consequences

**Positive:**
- Snapshot compression reduces storage by ~90% vs full trace capture (50MB→5MB per checkpoint for typical execution)
- Recovery is deterministic and verifiable (hash-gated, cursor-based, no re-derivation)
- Rollback enables safe retry within Mode 3 without restarting the full execution
- Pre-wave snapshots add negligible overhead (memory-only during execution)
- Trace provenance enables compliance verification of recovered executions
- Separation of snapshot (resume) from trace (replay) clarifies two distinct use cases

**Constraints:**
- Agent state compression loses detailed replan history — full history requires ADR-0004 traces
- Wave partition rebuilding on recovery is O(n²) but deterministic via total-order sort with node_id + rir_hash tie-breaker (SS-012)
- Rollback is limited to 3 per wave — complex failure modes may require full re-execution
- Cross-execution recovery requires matching runtime fingerprint (plugin versions, adapter versions, scheduler version) in addition to RIR and compiler hashes
- Snapshots are Mode 3 only — Mode 2 has no persistence surface
- Snapshot is a materialized derivation, not an independent source of truth — consistency with traces must be verified externally
- Rollback uses overlay markers only — traces remain immutable (OB-005)

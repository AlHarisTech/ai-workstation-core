# ADR-0003-E — Governance Engine

**Status:** PROPOSED
**Depends on:** ADR-0001 (Canonical Architecture), ADR-0002 (Compiler), ADR-0003-A (Execution Semantics), ADR-0003-B (Runtime Engine)
**Layer:** Cross-Cutting Control Plane
**Scope:** All execution modes. Governance applies at every system boundary: Router, Compiler, Runtime, and Plugins.

---

## 1. Core Thesis

```
The Governance Engine is a cross-cutting control plane
that never executes work directly.

It observes, constrains, and influences Router,
Compiler, Runtime, and Plugins exclusively through
policies, signals, and contracts.

Governance may admit, reject, defer, terminate,
escalate, annotate, or audit execution, but it never:

- mutates the CEG
- executes nodes
- dispatches plugins
- commits node state
- bypasses the Commit Engine
- derives new execution graphs
- rewrites RIR or spec artifacts
```

**Foundational architectural rule:**

```
Governance is a Control Plane.
Runtime is a Data Plane.

They share no state.
They share no execution path.
They communicate exclusively through signals.
```

## 2. Architectural Position

```
                        ┌───────────────────┐
                        │ GOVERNANCE ENGINE │
                        │  (Control Plane)  │
                        └────────┬──────────┘
                                 │
           ┌─────────────────────┼─────────────────────┐
           │ policies            │ policies            │ policies
           │ signals             │ signals             │ signals
           │                     │                     │
     ┌─────▼─────┐        ┌──────▼──────┐        ┌─────▼─────┐
     │  ROUTER   │        │  COMPILER   │        │  RUNTIME  │
     │(Data Plane)│       │(Data Plane) │        │(Data Plane)│
     └───────────┘        └─────────────┘        └─────┬─────┘
                                                       │
                                                 ┌─────▼─────┐
                                                 │  PLUGINS  │
                                                 │(Data Plane)│
                                                 └───────────┘
```

Governance sits **above** all data-plane components. Data-plane components never invoke Governance APIs directly. Data-plane components publish events to their own event buses. Governance subscribes to those events through a read-only Runtime Signal Adapter (§4.8). Governance emits signals that data-plane components consume. The communication is always asynchronous — never synchronous API calls.

│ └────┬─────┘  └────┬─────┘  └────┬─────┘  └───────┬───────┘   │

│                     │             │                            │
│                ┌────▼─────────────▼─────┐                      │
│                │  RISK ENGINE           │                      │
│                └────────────┬───────────┘                      │
│                             │                                  │
│                ┌────────────▼───────────┐                      │
│                │  ESCALATION MANAGER    │                      │
│                └────────────┬───────────┘                      │
│                             │                                  │
│                ┌────────────▼───────────┐                      │
│                │  COMPLIANCE & AUDIT    │                      │
│                └────────────┬───────────┘                      │
│                             │                                  │
│                ┌────────────▼───────────┐                      │
│                │  GOVERNANCE EVENT      │                      │
│                │  STREAM                │                      │
│                └────────────────────────┘                      │
└───────────────────────────────────────────────────────────────┘
```

| # | Component | Responsibility |
|---|-----------|---------------|
| 1 | **Admission Controller** | Controls entry into execution — admits, rejects, defers, or requires escalation |
| 2 | **Policy Evaluator** | Evaluates all governance policies against the current context; produces `PolicyDecision` |
| 3 | **Constraint Engine** | Validates hard constraints (security, resources, isolation) against the execution plan |
| 4 | **Capability Governor** | Enforces allowlists/denylists on capabilities, tools, providers, and cross-region operations |
| 5 | **Risk Engine** | Consumes policy violations, escalations, and failure signals; produces `RiskLevel` |
| 6 | **Escalation Manager** | Owns escalation contracts; emits `ESCALATE`/`TERMINATE` signals to the Coordinator |
| 7 | **Compliance & Audit Engine** | Produces immutable, append-only audit records of every governance decision |
| 8 | **Governance Event Stream** | Transient ordered delivery of governance-level events — separate from Runtime Event Bus |

## 4. Component Specifications

### 4.1 Admission Controller

```
admit(request, context)     → AdmissionDecision
revalidate(execution_id)    → AdmissionDecision    # for resume/deferral
```

**Decision space:**

```yaml
admission_decision:
  verdict: "PERMIT" | "DENY" | "DEFER" | "ESCALATE_REQUIRED"
  reason: "<string>"
  constraints: ["<constraint-ref>"]       # attached conditions if PERMIT
  escalation_target: "<role>" | null      # if ESCALATE_REQUIRED
  defer_deadline: "<iso8601>" | null       # if DEFER
  valid_until: "<iso8601>" | null          # expiration; null = permanent (PERMIT/DENY are permanent for the execution)
  decision_id: "<uuid>"
  issued_at: "<iso8601>"
  issued_by: "admission-controller"
```

**Expiration semantics (GI-019):**

```
PERMIT and DENY:     valid_until = null (permanent for this execution instance)
DEFER:               valid_until = defer_deadline (after which re-admission is required)
ESCALATE_REQUIRED:   valid_until = null (permanent — re-admission only after escalation is resolved)
```

**Admission gates:**

| Gate | Trigger | Behavior |
|------|---------|----------|
| **Mode admission** | Router selects execution mode | Validates mode is permitted for this request class |
| **Plugin admission** | Plugin registered or invoked | Validates plugin contract, compatibility, and isolation |
| **Resume admission** | `RESUME(snapshot_id)` requested | Validates snapshot hash compatibility and governance state |
| **Snapshot admission** | `create()` requested | Validates execution is in a checkpoint-permitted state |
| **Compilation admission** | Spec submitted to Pass 0 | Validates spec provenance, execution_mode, and required capabilities |

**Constraint (GI-011):** Admission decisions are final for a single execution instance. Revising a decision requires a new governance decision record, not mutation of the original.

### 4.2 Policy Evaluator

```
evaluate(policy_set, context) → PolicyDecision
```

**Input context:**

```yaml
evaluation_context:
  request:
    mode: "2" | "3"
    spec_ref: "<ref>"
    provenance: {}              # from ADR-0002-D §7
  execution_plan:
    rir_hash: "<sha256>"
    execution_plan_hash: "<sha256>"
    unit_count: <int>
    max_depth: <int>
    regions: ["<region-id>"]
  capabilities_required: ["<capability-ref>"]
  plugins_required: ["<plugin-id>"]
  runtime_signals: {}           # latest signals from Runtime
```

**Output:**

```yaml
policy_decision:
  decision_id: "<uuid>"
  verdict: "ALLOW" | "DENY" | "DEFER" | "ESCALATE" | "TERMINATE" | "ANNOTATE"
  matched_policies: ["<policy-ref>"]
  violations: ["<violation-ref>"]
  annotations: ["<string>"]
  issued_at: "<iso8601>"
```

**Determinism constraint (GI-005):**

```
Policy evaluation is a PURE FUNCTION.

Given identical (policy_set, context):
  → identical PolicyDecision

No randomness.
No time-dependent behavior.
No external state reads beyond the provided context.
```

**Policy manifest (GI-018):**

```yaml
policy_manifest:
  policy_set_id: "<uuid>"
  version: "<semver>"
  hash: "<sha256>"                   # SHA256 of complete policy set
  loaded_at: "<iso8601>"
  policies: ["<policy-ref>"]
```

A single execution observes exactly one policy manifest. Policies are loaded at execution start and are immutable for the duration of the execution. If policies change between admission and execution completion, those changes take effect only on the next execution instance.

### 4.3 Constraint Engine

```
validate(constraints, execution_context) → [ConstraintViolation]
```

**Constraint types:**

```yaml
constraint:
  id: "<uuid>"
  type: "HARD" | "SOFT"
  category: "SECURITY" | "RESOURCE" | "ISOLATION" | "CAPABILITY" | "POLICY"
  predicate: "<declarative-expression>"
  on_violation: "DENY" | "ESCALATE" | "WARN"
```

**Hard constraints (violation = execution blocked):**

| ID | Constraint | Category |
|----|-----------|----------|
| GC-001 | `execution_mode` must be permitted for this request class | SECURITY |
| GC-002 | All required capabilities must be present in the Capability Governor allowlist | CAPABILITY |
| GC-003 | Plugin isolation model must satisfy region isolation requirements | ISOLATION |
| GC-004 | No cross-region data_flow edge exists in CEG | ISOLATION |
| GC-005 | `execution_plan.max_parallelism` does not exceed configured resource limit | RESOURCE |
| GC-006 | Spec provenance hash matches a trusted source | SECURITY |

**Soft constraints (violation = annotation + advisory only):**

| ID | Constraint | Category |
|----|-----------|----------|
| GC-S01 | Unit count exceeds recommended threshold for this mode | RESOURCE |
| GC-S02 | CEG depth approaches maximum (≥ 120) | RESOURCE |
| GC-S03 | Plugin has error history in current window | CAPABILITY |

**Constraint Engine NEVER:**
- Modifies the execution plan to resolve violations
- Retries with different parameters
- Executes remediation actions
- Blocks execution for SOFT violations

### 4.4 Capability Governor

```
define_contract(capabilities, context) → CapabilityContract
restrict(capability_ref, scope)        → CapabilityContract  # monotonic narrowing only
```

**The Capability Governor never interacts with the Dispatcher at execution time.** It produces a `CapabilityContract` at admission time. The Dispatcher enforces the contract locally during execution without calling Governance.

**Capability contract (produced by governance, enforced by runtime):**

```yaml
capability_contract:
  contract_id: "<uuid>"
  issued_at: "<iso8601>"
  entries:
    - ref: "<capability-ref>"
      state: "ALLOWED" | "DENIED" | "SCOPED"
      scope:
        filesystem: "none" | "read_only:<path>" | "scoped:<path>"
        network: "none" | "restricted:<domain-list>"
        max_tokens: <int> | null
        max_duration_ms: <int>
      restrictions_applied_at: "<iso8601>"
```

**Runtime enforcement (by Dispatcher, NOT Governance):**

```
The Dispatcher receives the CapabilityContract in its execution context.
Before every plugin invocation:
  1. Look up capability in contract
  2. If DENIED → reject invocation
  3. If SCOPED → apply scope constraints at isolation boundary
  4. If ALLOWED → proceed
The Dispatcher never calls Governance during execution.
```

**Invariant (GI-014):**

```
GI-014: Data-plane components never synchronously call
Governance services during execution.

Governance decisions are materialized as immutable
contracts consumed by the Runtime. The Runtime
enforces contracts locally without governance interaction.
```

**Monotonicity constraint (GI-012):**

```
Capability restrictions are monotonic during one execution.

ALLOWED → SCOPED   (permitted — scope narrows)
SCOPED  → DENIED   (permitted — scope narrows further)
DENIED  → ALLOWED  (FORBIDDEN — cannot widen scope)
ALLOWED → DENIED   (permitted — scope narrows)
```

A capability once restricted cannot be re-widened within the same execution. This prevents runtime privilege escalation.

### 4.5 Risk Engine

```
assess(risk_context) → RiskAssessment
```

**Risk is advisory.** Risk alone does not block, terminate, or escalate execution. It feeds the Escalation Manager and informs Policy Evaluator context.

**The Risk Engine is stateful by design.** Unlike the Policy Evaluator (pure function per GI-005), the Risk Engine aggregates signals over time. However, determinism is preserved within a single execution: given the same accumulated risk_context, the Risk Engine produces the same RiskAssessment.

**Input context (complete historical snapshot):**

```yaml
risk_context:
  execution_id: "<uuid>"
  window:
    type: "sliding"               # sliding execution-local window — the Risk Engine never performs external history queries
    since: "<iso8601>"            # start of aggregation window
    until: "<iso8601>"            # current time
  violations:
    - type: "<violation-type>"
      count: <int>
      last_at: "<iso8601>"
  escalations:
    - reason: "<string>"
      count: <int>
  plugin_failures:
    - plugin_id: "<uuid>"
      error_count: <int>
      crash_count: <int>
      last_error_at: "<iso8601>"
  isolation_events:
    - type: "<event-type>"
      count: <int>
  security_signals: ["<signal-ref>"]
  current_risk_level: "LOW" | "MEDIUM" | "HIGH" | "CRITICAL"

**Output:**

```yaml
risk_assessment:
  assessment_id: "<uuid>"
  level: "LOW" | "MEDIUM" | "HIGH" | "CRITICAL"
  contributing_signals: ["<signal-ref>"]
  trend: "STABLE" | "ESCALATING" | "DEESCALATING"
  recommendation: "NONE" | "MONITOR" | "ESCALATE" | "TERMINATE"
  issued_at: "<iso8601>"
```

### 4.6 Escalation Manager

```
request_escalation(reason, context)  → EscalationSignal
request_termination(reason, context) → TerminationSignal
```

**Escalation contracts:**

```yaml
escalation_contract:
  id: "<uuid>"
  priority: <int>                     # lower = higher priority (0 is highest)
  trigger:
    risk_level: "HIGH" | "CRITICAL"
    violation_type: "<constraint-category>"
    failure_pattern: "<pattern-ref>"
  action: "ESCALATE" | "TERMINATE"
  target: "ROUTER" | "COORDINATOR"
  reason_template: "<string>"
```

**Contract evaluation order (GI-020):**

```
When multiple escalation contracts fire simultaneously:

  1. TERMINATE contracts are evaluated first
  2. Then DENY
  3. Then ESCALATE
  4. Then DEFER
  5. Finally ANNOTATE

Within the same action type, lower priority value wins.
If priority is equal, the contract with the most specific trigger wins.
```

**Emitted signals (never executed — only emitted):**

```yaml
governance_signal:
  signal_id: "<uuid>"
  signal_type: "ESCALATE" | "TERMINATE" | "DEFER" | "ANNOTATE"
  signal_class: "MANDATORY" | "ADVISORY"   # per §6.1
  target_component: "ROUTER" | "COORDINATOR"
  reason: "<string>"
  context_ref: "<execution-id>"
  emitted_at: "<iso8601>"
  emitted_by: "escalation-manager"
```

**Constraint (GI-010):**

```
The Escalation Manager may RECOMMEND termination.
It never PERFORMS termination.

Only the Runtime Coordinator executes TERMINATE.
Only the Compiler aborts its own pipeline.
The Escalation Manager EMITS SIGNALS exclusively.
```

### 4.7 Compliance & Audit Engine

```
record(decision)    → AuditEntry
query(filter)       → [AuditEntry]
export(from, to)    → AuditReport
```

**Audit entry schema:**

```yaml
audit_entry:
  entry_id: "<uuid>"
  sequence: <uint64>                # monotonic within governance stream, scoped per execution
  timestamp: "<iso8601>"
  source_component: "<component-name>"
  entry_type: "POLICY_DECISION" | "ADMISSION_DECISION" |
              "CONSTRAINT_VIOLATION" | "RISK_ASSESSMENT" |
              "ESCALATION_SIGNAL" | "TERMINATION_SIGNAL" |
              "CAPABILITY_RESTRICTION" | "EXECUTION_ANNOTATION"
  policy_manifest_hash: "<sha256>"  # which policy set governed this decision — enables full reconstruction
  payload: {}                       # component-specific decision payload
  immutable: true
```

**Properties (GI-004):**

```
All governance decisions are:
- Append-only
- Immutable (never modified after creation)
- Auditable (full history queryable)
- Replayable (sequence-ordered for reconstruction)
- Separated from Runtime Journal (different stream, different storage)
```

### 4.8 Governance Event Stream

```
publish(event)    → void
subscribe(pattern)→ Subscription
```

**Critical separation:**

```
┌──────────────────────────────┐  ┌──────────────────────────────┐
│ GOVERNANCE EVENT STREAM      │  │ RUNTIME EVENT BUS            │
│ (Control Plane)              │  │ (Data Plane)                 │
│                              │  │                              │
│ PolicyEvaluated              │  │ NodeStarted                  │
│ AdmissionRejected            │  │ NodeCommitted                │
│ RiskRaised                  │  │ NodeFailed                   │
│ EscalationRequested          │  │ NodeTerminated               │
│ ExecutionDeferred            │  │ WaveCompleted                │
│ CapabilityRestricted         │  │ EscalationRaised             │
│ ConstraintViolationDetected  │  │ RuntimeAborted               │
│ TerminationRecommended       │  │ CheckpointCreated            │
│ ExecutionAnnotated           │  │                              │
└──────────────────────────────┘  └──────────────────────────────┘
```

**Why separation matters:**
- Governance events inform control-plane decisions (policy, compliance, audit)
- Runtime events inform execution state (scheduling, commit, recovery)
- Merging them would couple control-plane latency to execution throughput
- Separating them enables independent scaling, storage, and retention policies
- Governance events may need longer retention than runtime events

**Constraints (GI-009):**

```
Governance and Runtime event streams are strictly separated.
No component may bridge them without explicit governance approval.

The ONLY bridge between the two streams is the Runtime Signal Adapter:
  - A read-only subscriber on the Runtime Event Bus
  - Translates selected Runtime events into Governance Event Stream entries
  - Never writes to the Runtime Event Bus
  - Governance components subscribe to the Governance Event Stream, not the Runtime Event Bus
```

**Runtime Signal Adapter (Bridge):**

```yaml
runtime_signal_adapter:
  subscribes_to: "Runtime Event Bus"
  publishes_to: "Governance Event Stream"
  access: "READ_ONLY"
  event_filter:
    include:
      - "NodeFailed"
      - "NodeTerminated"
      - "EscalationRaised"
      - "RuntimeAborted"
      - "CheckpointCreated"
    exclude:
      - "NodeStarted"          # internal scheduling, not governance-relevant
      - "NodeCommitted"        # too granular for governance
      - "WaveCompleted"        # derivable from NodeCommitted
```

**Invariant (GI-013):**

```
GI-013: Runtime events may be observed by Governance only
through a read-only Runtime Signal Adapter. No governance
component may subscribe directly to the Runtime Event Bus.
```

**Invariant (GI-022):**

```
GI-022: The Runtime Signal Adapter is strictly unidirectional.

Events originating from the Governance Event Stream
MUST NEVER be republished to the Runtime Event Bus.
The adapter reads from Runtime, writes to Governance — never the reverse.

This prevents infinite feedback loops:
  Runtime → Adapter → Governance → Signal → Runtime → Adapter → …
```

**Event ordering (GI-008):**

```
Governance event ordering is deterministic within one execution.

Sequence numbers are monotonic within the governance stream.
Order is determined by the sequence of PolicyEvaluator invocations
and signal emissions — not by wall-clock time.
```

## 5. Governance Flows

### 5.1 Execution Admission Flow

```
ROUTER                   ADMISSION CTRL        POLICY EVAL        CONSTRAINT ENG
   │                          │                     │                   │
   │──admit(request)─────────►│                     │                   │
   │                          │──evaluate(policies)─►│                   │
   │                          │                     │──validate()──────►│
   │                          │                     │                   │
   │                          │◄──PolicyDecision────│                   │
   │                          │                     │◄──violations──────│
   │                          │                     │                   │
   │                          │──assess(risk)──────────────────────────►│
   │                          │◄──RiskAssessment────────────────────────│
   │                          │                     │                   │
   │◄──AdmissionDecision──────│                     │                   │
   │                          │                     │                   │
   │  if PERMIT: continue     │                     │                   │
   │  if DENY:   reject       │                     │                   │
   │  if DEFER:  queue        │                     │                   │
   │  if ESCALATE_REQUIRED:   │                     │                   │
   │    emit EscalationSignal │                     │                   │
```

### 5.2 Runtime Monitoring Flow

```
RUNTIME ENGINE       RUNTIME EVENT BUS    SIGNAL ADAPTER    GOVERNANCE ENGINE
     │                      │                    │                   │
     │──NodeFailed─────────►│                    │                   │
     │                      │──filtered event───►│                   │
     │                      │                    │──governance_event►│
     │                      │                    │                   │──RiskEngine.assess()
     │                      │                    │                   │──EscalationManager.evaluate()
     │                      │                    │                   │
     │◄──signal(TERMINATE)────────────────────────────────────────────│  (if risk CRITICAL)
     │                      │                    │                   │
     │ or                   │                    │                   │
     │◄──signal(ESCALATE)────────────────────────────────────────────│  (if risk HIGH)
     │                      │                    │                   │
     │ or                   │                    │                   │
     │◄──signal(ANNOTATE)────────────────────────────────────────────│  (if risk MEDIUM)
```

### 5.3 Capability Contract Enforcement Flow

```
ADMISSION                    CAPABILITY GOVERNOR          DISPATCHER (Runtime)
     │                              │                            │
     │──resolve capabilities───────►│                            │
     │                              │──build contract            │
     │◄──CapabilityContract─────────│                            │
     │                              │                            │
     │  contract embedded in        │                            │
     │  execution context ──────────────────────────────────────►│
     │                              │                            │
     │                              │     (later, at dispatch)   │
     │                              │     Dispatcher reads       │
     │                              │     contract locally       │
     │                              │     enforces scope at      │
     │                              │     isolation boundary     │
     │                              │                            │
     │                              │     NO governance call     │
     │                              │     during execution       │
```

The Dispatcher enforces the capability contract locally. It never calls the Capability Governor at execution time. The contract is immutable for the duration of the execution.

## 6. Governance Signals

### 6.1 Signal Catalog

**Mandatory signals** (MUST be honored by target component; failure to honor = ABORT + audit escalation):

| Signal | Emitted By | Consumed By | Effect |
|--------|-----------|-------------|--------|
| `TERMINATE` | Escalation Manager | Runtime Coordinator | Coordinator MUST issue `TerminateRequest` to Commit Engine |
| `DENY` | Admission Controller | Router | Router MUST reject execution |
| `RESTRICT` | Capability Governor | Dispatcher | Dispatcher MUST narrow scope for subsequent invocations |

**Advisory signals** (inform action; target component evaluates and decides):

| Signal | Emitted By | Consumed By | Effect |
|--------|-----------|-------------|--------|
| `ESCALATE` | Escalation Manager | Router | Router evaluates reclassification (F-004) |
| `DEFER` | Admission Controller | Router | Router may queue execution |
| `ANNOTATE` | Policy Evaluator | Compliance Engine | Annotation appended to execution audit trail |

**Invariant (GI-015):**

```
GI-015: Mandatory governance signals (TERMINATE, DENY, RESTRICT)
MUST be honored by target components.

Failure to honor a mandatory signal causes runtime ABORT
and an audit escalation event recording the violation.
```

### 6.2 Signal Lifecycle

```
EMIT (by governance component)
  → APPEND to Governance Event Stream
    → DELIVER to target component
      → ACKNOWLEDGE (target component confirms receipt — delivery ACK only)
        → ACT (target component executes the signal's prescribed action — asynchronous)
```

**Delivery ACK vs Action Completion:**

```
Governance waits ONLY for delivery acknowledgement.

Execution of the signal action is asynchronous.
Governance verifies that the action occurred by observing
subsequent Runtime events and audit records — not by
waiting for the action to complete synchronously.

For Mandatory signals (TERMINATE, DENY, RESTRICT):
  - Delivery ACK confirms the signal was received
  - GI-021 governs verification that the signal was honored
  - Failure to observe expected post-condition within timeout → ABORT
```

**Invariant (GI-021):**

```
GI-021: Failure to observe the expected post-condition of a Mandatory
signal within a bounded timeout constitutes a protocol violation
and triggers ABORT + audit escalation.

Timeout is defined per signal type:
  TERMINATE: 5s from delivery ACK
  DENY:      1s from delivery ACK
  RESTRICT:  500ms from delivery ACK
```

## 7. Integration Contracts

### 7.1 Router ↔ Governance

```
Router invokes:  AdmissionController.admit(request, context)
Router receives: AdmissionDecision
Router obeys:    PERMIT → proceed; DENY → reject; DEFER → queue; ESCALATE_REQUIRED → escalate

Governance may:  Reject modes incompatible with policy
Governance never: Selects the mode — that remains Router's responsibility
```

### 7.2 Compiler ↔ Governance

```
Compiler invokes:  AdmissionController.admit(spec, context)  # pre-Pass 0
Compiler receives: AdmissionDecision
Compiler obeys:    PERMIT → begin Pass 0; DENY → abort compilation

Governance may:  Reject specs with prohibited capabilities or untrusted provenance
Governance never: Modifies the spec, influences pass semantics, or rewrites RIR
```

### 7.3 Runtime ↔ Governance

```
Runtime publishes:   Events to Runtime Event Bus (NodeFailed, EscalationRaised, RuntimeAborted, CheckpointCreated)
Signal Adapter:      Subscribes to Runtime Event Bus (read-only), translates selected events into Governance Event Stream
Governance consumes: Governance Event Stream entries (not Runtime Event Bus directly)
Governance emits:    TERMINATE, ESCALATE, ANNOTATE

Runtime receives:    Governance signals
Runtime obeys:       TERMINATE → Coordinator.terminate(); ANNOTATE → log to Journal

Governance may:      Recommend termination or escalation based on runtime behavior
Governance never:    Commits node state, dispatches plugins, modifies CEG, subscribes to Runtime Event Bus directly
```

### 7.4 Plugin ↔ Governance

```
Plugin registers:  Via Plugin Registry (ADR-0002-E)
Governance validates: Plugin contract, isolation model, capability claims, compatibility
Governance decision: Admit or reject plugin activation

Governance may:  Restrict capability scope post-admission (monotonic narrowing)
Governance never: Invokes plugin code, inspects plugin internals, or bypasses Dispatcher
```

## 9. Failure Semantics

### 9.1 Governance Component Failure

| Component | Failure Mode | System Impact |
|-----------|-------------|---------------|
| Admission Controller | Unavailable | Execution rejected (fail-closed) — no admission without governance |
| Policy Evaluator | Unavailable | Execution rejected (fail-closed) — no policy check = no execution |
| Constraint Engine | Unavailable | Execution rejected (fail-closed) — constraints unvalidated |
| Capability Governor | Unavailable | All capabilities DENIED — execution may continue with zero capabilities |
| Risk Engine | Degraded | Risk assessments pause; escalation manager operates on last-known risk level |
| Escalation Manager | Unavailable | No escalation signals emitted; execution continues under last-known governance state |
| Compliance & Audit | Unavailable | Governance events appended to durable local spool; replayed on recovery — no data loss (GI-016) |
| Governance Event Stream | Unavailable | Governance signals undelivered; Runtime continues under last-known governance state |

### 9.2 Governance Decision Conflicts

```
If two governance components produce conflicting signals:

  1. DENY always overrides PERMIT (security-first)
  2. TERMINATE always overrides ESCALATE (safety-first)
  3. Latest constraint violation overrides earlier scope grant
  4. Conflict is recorded as an audit event with both decisions attached
```

### 9.3 Governance Degradation Mode

```
If Governance Engine is partially available:

  1. Admission Controller + Policy Evaluator → REQUIRED (unavailable = no execution)
  2. Constraint Engine → REQUIRED (unavailable = no execution)
  3. All other components → DEGRADED (execution continues with reduced governance)
  4. Degraded execution is annotated in the audit trail
  5. Degraded execution has elevated risk level (minimum MEDIUM)
```

## 10. Component Boundaries (What Each Component Does NOT Do)

| Component | Does NOT |
|-----------|----------|
| Admission Controller | Execute work, schedule nodes, modify CEG |
| Policy Evaluator | Access runtime state beyond provided context, mutate execution |
| Constraint Engine | Remediate violations, modify execution plan |
| Capability Governor | Invoke capabilities, execute tools, dispatch agents |
| Risk Engine | Block execution, terminate nodes, override admission decisions |
| Escalation Manager | Execute termination, mutating CEG, commit node state |
| Compliance & Audit | Publish to Runtime Event Bus, modify decisions after creation |
| Governance Event Stream | Persist events (that's Compliance & Audit), guarantee delivery to data-plane |

## 11. Implementation Guidance (Non-Normative)

- **Language:** Pure functions preferred. Policy evaluator and constraint engine benefit from declarative expression languages (e.g., Rego/OPA-style) rather than imperative code.
- **Storage:** Compliance & Audit entries are stored separately from Runtime Journal. SQLite (same pattern as Journal) for v1, with a separate database per execution for isolation.
- **Latency budget:** Governance decision at admission time must complete within 500ms (v1). Runtime monitoring signals must be processed within 100ms of receipt.
- **Policy format:** Declarative YAML with predicate expressions (same assertion language deferred in Q2, ADR-0002-A §11). Policies are versioned and hashed for auditability.

## 13. Decision Outcome

The Governance Engine is defined as a cross-cutting control plane that operates exclusively through policies, signals, and contracts. It never executes work, never mutates CEG, never commits node state, and never bypasses the Commit Engine. It maintains a strict separation between its own Governance Event Stream and the Runtime Event Bus (GI-009), connected only by a strictly unidirectional, read-only Runtime Signal Adapter (GI-013, GI-022). Data-plane components never synchronously invoke Governance — all governance decisions are materialized as immutable contracts enforced locally by the Runtime (GI-014). Signals are classified as Mandatory (TERMINATE, DENY, RESTRICT — must be honored, with bounded verification timeout; GI-015, GI-021) or Advisory (ESCALATE, DEFER, ANNOTATE — evaluated by the target component). Governance waits only for delivery acknowledgement, not action completion — post-condition verification is asynchronous. All governance decisions are deterministic (GI-005), auditable with policy provenance (GI-004, policy_manifest_hash), durably recorded before acknowledgement (GI-016), and immutable once emitted (GI-006). Admission is fail-closed — governance unavailability blocks execution. Risk is advisory, computed over a sliding execution-local window. Capability restrictions are monotonic within a single execution (GI-012). Escalation contracts are evaluated by a fixed priority order (GI-020). Sequence numbers are scoped per execution, allocated by the Compliance & Audit Engine (GI-017).

## 14. Consequences

**Positive:**
- Clear Control Plane / Data Plane boundary prevents governance from becoming a second runtime
- Deterministic policy evaluation enables policy testing without execution
- Separate event streams prevent control-plane latency from coupling to execution throughput
- Admission Controller as single gate for all execution modes ensures consistent policy enforcement
- Monotonic capability restrictions prevent runtime privilege escalation
- Full audit trail of every governance decision, independent of runtime events

**Constraints:**
- Governance unavailability = execution blocked (fail-closed) — requires high governance reliability
- No dynamic policy changes within an execution — policies are fixed at admission time per immutable manifest (GI-018)
- Risk is advisory only — governance cannot preemptively block an execution based on risk alone
- Mandatory signals (TERMINATE, DENY, RESTRICT) MUST be honored — target component failure to honor = ABORT (GI-015)
- Capability Governor cannot widen scope mid-execution — this may require re-execution if a capability becomes necessary later
- Runtime Signal Adapter is the sole bridge between the two event streams — adds latency for governance to observe runtime events
- All governance decisions are durably recorded (GI-016) — adds write latency before signal acknowledgement
- Admission decisions may expire (GI-019) — deferred or escalated executions require re-admission after expiration

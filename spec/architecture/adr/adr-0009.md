# ADR-0009 — Cross-Layer Feedback & Adaptive Control

**Status:** PROPOSED
**Depends on:** MEK v1.4 (Closed Formal Execution System), ADR-0006 (Consistency Controller)
**Layer:** System Integration — Adaptive Control
**Scope:** External to MEK. Sits ABOVE the verification substrate. Never modifies MEK internals.

---

## 1. Core Thesis

```
ADR-0009 is a cross-layer feedback controller that consumes
MEK verification signals (PASS / FAIL / DRIFT / DIVERGENCE)
and translates them into adaptive actions for any application.

It does NOT modify MEK.
It does NOT contain business logic.
It does NOT make policy decisions.

It CLOSES THE LOOP between:
  - deterministic verification (MEK)
  - adaptive application behavior (any project)
```

## 3. Layer 1 — Signal Ingestor

### 3.1 Purpose

Consume raw MEK output and normalize it into structured signals.

### 3.2 Signal Schema

```yaml
mek_signal:
  signal_id: "<uuid>"
  timestamp: "<iso8601>"
  source:
    execution_id: "<uuid>"
    project_ref: "<string>"
    rir_hash: "<sha256>"

  # Verification result (from MEK)
  verification:
    kernel:        "PASS" | "FAIL"
    journal:       "PASS" | "FAIL"
    trace:         "PASS" | "FAIL"
    replay:        "PASS" | "FAIL" | "DIVERGENCE"
    structural:    "PASS" | "FAIL"
    consistency:   "PASS" | "FAIL"

  # Divergences (if any)
  divergences:
    - domain: "kernel↔replay" | "journal↔trace" | ...
      node_id: "<uuid>"
      expected: "<status>"
      actual: "<status>"

  # Metrics
  metrics:
    total_duration_ms: <int>
    nodes_executed: <int>
    waves_completed: <int>
    escalation_requested: true | false

  # Drift indicators (from ADR-0006 ECCC)
  drift:
    detected: true | false
    class: "STRUCTURAL" | "TEMPORAL" | "SEQUENCE" | "UNSPECIFIED"
    severity: "LOW" | "MEDIUM" | "CRITICAL"
```

### 3.3 Signal Classification

| Signal State | Meaning | Adaptive Response |
|-------------|---------|-------------------|
| `ALL_PASS` | Every domain passes | System is stable — no action |
| `PARTIAL_FAIL` | One domain failed | Investigate — potential false alarm or real issue |
| `REPLAY_DIVERGENCE` | Replay ≠ Kernel | Determinism violation — re-execute or flag |
| `STRUCTURAL_FAIL` | Graph constraints violated | Fix the execution plan |
| `DRIFT_DETECTED` | Cross-domain inconsistency | Escalate to application for resolution |
| `CONSISTENCY_FAIL` | Lattice broken | Critical — halt dependent operations |

## 4. Layer 2 — Feedback Controller

### 4.1 Purpose

Map MEK signals to application-level actions through a configurable rule engine.

### 4.2 Feedback Rules

```yaml
feedback_rule:
  rule_id: "<uuid>"
  condition:
    signal_state: "ALL_PASS" | "PARTIAL_FAIL" | "DRIFT_DETECTED" | ...
    min_occurrences: <int>            # how many times before action
    window: "<duration>"              # time window for occurrences
  action:
    type: "NOTIFY" | "REEXECUTE" | "ROLLBACK" | "ESCALATE" | "HALT"
    target: "<application-endpoint>"
    payload: {}                       # additional context
    cooldown: "<duration>"            # minimum time between actions
```

### 4.3 Built-in Rules (v1)

| Rule | Condition | Action |
|------|-----------|--------|
| `R01` | ALL_PASS × 3 consecutive | NOTIFY: "system stable" |
| `R02` | REPLAY_DIVERGENCE × 1 | REEXECUTE: re-run the workflow |
| `R03` | STRUCTURAL_FAIL × 1 | NOTIFY + HALT dependent ops |
| `R04` | DRIFT_DETECTED (CRITICAL) × 1 | ESCALATE: trigger incident |
| `R05` | DRIFT_DETECTED (LOW) × 5 in window(1h) | NOTIFY: "degradation trend" |
| `R06` | CONSISTENCY_FAIL × 1 | HALT: stop all dependent workflows |

## 5. Layer 3 — Drift Predictor

### 5.1 Purpose

Analyze signal history to predict future divergence before it becomes critical.

### 5.2 Prediction Model

```yaml
drift_prediction:
  prediction_id: "<uuid>"
  generated_at: "<iso8601>"
  horizon: "<duration>"                # how far ahead

  # Trend analysis
  trend:
    direction: "STABLE" | "DEGRADING" | "IMPROVING"
    confidence: 0.0..1.0
    based_on_signals: <int>            # sample size

  # Predicted state
  predicted:
    state: "ALL_PASS" | "PARTIAL_FAIL" | "DRIFT_DETECTED" | ...
    probability: 0.0..1.0
    earliest_at: "<iso8601>" | null

  # Contributing factors
  factors:
    - factor: "replay_divergence_rate"
      weight: 0.0..1.0
    - factor: "structural_fail_rate"
      weight: 0.0..1.0
    - factor: "execution_duration_trend"
      weight: 0.0..1.0
```

### 5.3 Prediction Rules (v1 — Deterministic)

The Drift Predictor in v1 uses **deterministic trend analysis**, not ML:

```
PREDICT(signal_history, horizon):
  1. Compute rate of change for each signal class
  2. If replay_divergence_rate > 0:
     predicted.state ← "REPLAY_DIVERGENCE"
     predicted.probability ← min(1.0, rate × horizon)
  3. If structural_fail_rate > 0:
     predicted.state ← "STRUCTURAL_FAIL"
     predicted.probability ← 1.0  # structural fails are deterministic
  4. If drift_detected_rate is increasing:
     predicted.state ← "DRIFT_DETECTED"
     predicted.probability ← trend_confidence
  5. Otherwise:
     predicted.state ← "ALL_PASS"
     predicted.probability ← 1.0 - max(rates)
```

## 6. Action Bus

### 6.1 Purpose

Deliver adaptive actions to application endpoints without coupling.

### 6.2 Bus Schema

```yaml
adaptive_action:
  action_id: "<uuid>"
  triggered_by:
    rule_id: "<uuid>"
    signal_id: "<uuid>"
  type: "NOTIFY" | "REEXECUTE" | "ROLLBACK" | "ESCALATE" | "HALT"
  target: "<application-endpoint>"
  payload:
    signal_summary: "<string>"
    recommended_action: "<string>"
    affected_nodes: ["<uuid>"]
    divergence_details: []
  issued_at: "<iso8601>"
  ttl: "<duration>" | null
```

### 6.3 Delivery Guarantees

```
✓ At-least-once delivery to application endpoint
✓ Ordered by signal timestamp
✓ No action is silently dropped
✓ TTL-based expiration (stale actions are discarded)
✗ No guaranteed response from application (fire-and-adapt)
```

## 7. Integration Contract

### 7.1 MEK → ADR-0009

```
MEK produces:   Verification results (StatusMap, Report, ConsistencyReport)
ADR-0009 consumes: Results via file/stdout or API
ADR-0009 transforms: Raw results → Signal schema
ADR-0009 never: Modifies MEK, re-executes MEK, or changes MEK configuration
```

### 7.2 ADR-0009 → Application

```
ADR-0009 produces: AdaptiveAction on the Action Bus
Application consumes: Actions via webhook, message queue, or CLI callback
Application responds: By adjusting its own state/behavior
ADR-0009 never: Modifies application internals or makes business decisions
```

### 7.3 Application Independence

```
Each application registers its own feedback rules.
Applications do not share feedback state.
MEK verification is stateless per execution.
The controller is multi-tenant but isolated per application.
```

## 9. Operational Flow

```
Application executes a workflow
        │
        ▼
MEK verifies the execution
        │
        ▼
ADR-0009 ingests verification signals
        │
        ├── ALL_PASS ──► no action (system stable)
        │
        ├── REPLAY_DIVERGENCE ──► REEXECUTE action → Application re-runs
        │
        ├── STRUCTURAL_FAIL ──► HALT action → Application stops dependent ops
        │
        ├── DRIFT_DETECTED ──► NOTIFY or ESCALATE → Application adapts
        │
        └── CONSISTENCY_FAIL ──► HALT → Critical incident
                │
                ▼
        Application receives action → adapts → re-executes → loop closes
```

## 10. System Levels (Per This ADR)

| Level | System | Achieved By |
|-------|--------|-------------|
| **L1 — Static** | One-shot execution | MEK alone |
| **L2 — Reactive** | MEK signals consumed | Signal Ingestor |
| **L3 — Adaptive** | Rules trigger actions | Feedback Controller |
| **L4 — Predictive** | Drift forecast before failure | Drift Predictor |
| **L5 — Optimizing** | Multi-objective control | Future (goal conflict resolution) |

ADR-0009 delivers **L3 (Adaptive)** in v1 and **L4 (Predictive)** in v1 with deterministic trend analysis.

---

## 11. Decision Outcome

ADR-0009 defines a cross-layer feedback controller that consumes MEK verification signals and produces adaptive actions for any application. It sits ABOVE MEK (never inside), maintains per-application isolation, and uses deterministic feedback rules. The Drift Predictor uses trend-based analysis (not ML) to forecast divergence. The Action Bus delivers recommendations to applications without coupling. MEK remains an independent, immutable, stateless verification substrate.

---

## 12. Consequences

**Positive:**
- MEK becomes a shared verification substrate for all projects
- Applications gain closed-loop adaptive behavior without modifying MEK
- Feedback rules are deterministic and auditable
- Drift prediction enables proactive intervention before failure
- Per-application isolation prevents cross-contamination

**Constraints:**
- ADR-0009 cannot fix MEK-detected problems — only recommend actions
- Drift prediction is trend-based (v1) — complex patterns require future ML extension
- Action delivery is fire-and-adapt — applications may ignore recommendations
- No cross-application optimization in v1
- MEK must be invoked externally — not embedded in application runtime

# ADR-0003-C — Agent Adapters

**Status:** PROPOSED
**Depends on:** ADR-0003-B (Runtime Engine), ADR-0003-D (Tool Adapters), ADR-0003-E (Governance Engine), ADR-0002-E (Plugin Architecture)
**Layer:** Runtime Core — Execution Adapters
**Scope:** Mode 2 / Mode 3. Mode 0/1 are bypass paths.

---

## 1. Core Thesis

```
An Agent Adapter is an orchestrator that composes tool invocations
into a coherent execution sequence within a single CEG agent node.

Agents consume tools. Tools are the primitives. Agents are the composers.

Every agent invocation flows through the Dispatcher.
The Dispatcher enforces the CapabilityContract locally.
Agents have state (session, context, plan), unlike stateless tools.

An agent is bound to a single CEG node and executes within
that node's scope, isolation region, and scheduling constraints.
```

## 2. Agent Position in the Execution Stack

```
CEG Agent Node (type: agent)
       │
       ▼
Dispatcher.resolve()
       │
       ▼
Agent Adapter
       │
       ├── Plan Engine (optional — Mode 2/3 only)
       │     │
       │     └── Generate tool invocation sequence
       │
       ├── Tool Orchestrator
       │     │
       │     ├── invoke(tool_A) → normalize result
       │     ├── invoke(tool_B) → normalize result
       │     └── invoke(tool_C) → normalize result
       │
       ├── Context Manager
       │     ├── session state
       │     ├── tool result aggregation
       │     └── artifact accumulation
       │
       └── Handoff Emitter
             └── Produce final AgentResult
       │
       ▼
Result Normalizer (per agent type)
       │
       ▼
Commit Engine
```

The agent does NOT bypass the tool pipeline. Every tool invocation within an agent goes through the same Tool Adapter → Result Normalizer path as a standalone capability node.

## 3. Agent Contract

```yaml
agent_contract:
  agent_id: "<uuid>"
  name: "<string>"
  version: "<semver>"

  # Capability mapping
  capability_ref: "<capability-ref>"      # what this agent provides

  # Tools this agent is permitted to invoke
  tool_allowlist:
    - tool_ref: "<tool-id>"
      max_invocations: <int> | null       # null = unlimited
      scope: "full" | "restricted"        # restricted = reduced input/output surface

  # Agent behavior
  orchestration:
    model: "reactive" | "planned" | "autonomous"
    max_tool_invocations: <int>            # hard limit — prevents runaway loops
    max_duration_ms: <int>                 # agent-level timeout
    max_tokens: <int> | null               # total tokens across all LLM calls

  # Plan engine (only for model = "planned" | "autonomous")
  plan:
    max_depth: <int>                      # max plan steps
    replan_enabled: true | false           # can the agent revise its plan?
    replan_max_iterations: <int>          # max replan cycles

  # State
  state:
    model: "stateless" | "session" | "checkpoint"
    max_session_duration_ms: <int> | null
    context_size_limit_tokens: <int> | null

  # Isolation
  isolation:
    model: "process" | "container" | "virtual"
    filesystem_access: "none" | "read_only:<path>" | "scoped:<path>"
    network_access: "none" | "restricted:<domain-list>"
    memory_limit_mb: <int>
    timeout_ms: <int>

  # Side effects (agent-level — superset of tool-level side effects)
  side_effect_surface:
    - "fs:<path>"
    - "network:<domain>"
    - "db:<resource>"

  # Handoff
  handoff:
    artifacts: ["<artifact-key>"]
    evidence: ["<evidence-key>"]
    next_agent: "<agent-ref>" | null

  # Validation
  validation:
    self_check:
      command: "<string>"
      expected_output: "<regex>" | null
```

## 4. Agent Orchestration Models

### 4.1 Reactive

```
The agent reacts to a single prompt with a single response.
No internal planning. No tool sequences. No replanning.

Flow:
  Input → Provider (LLM) → Output

Use cases:
  - Code generation from a spec snippet
  - Answer a technical question
  - Translate text
  - Summarize content

State: stateless
Tools: 0-1 tools invoked implicitly by the LLM provider
```

### 4.2 Planned

```
The agent generates a plan, then executes tools step by step.
Plan is fixed before execution. No replanning mid-execution.

Flow:
  Input → Plan → [invoke(tool_A) → invoke(tool_B) → ...] → Aggregate → Output

Use cases:
  - Implement a feature from a PRD (specified steps)
  - Run a predefined test suite
  - Execute a CI/CD pipeline
  - Batch data processing

State: session (plan + intermediate results)
Replan: disabled by default
```

### 4.3 Autonomous

```
The agent generates a plan, executes tools, observes results,
and may replan when tool results diverge from expectations.

Flow:
  Input → Plan → [invoke → observe → replan? → invoke → ...] → Output

Use cases:
  - Debug a complex bug (unknown root cause)
  - Autonomous code generation with self-review
  - Research task requiring exploration
  - Multi-step migration with rollback on failure

State: session (plan + intermediate + replan history)
Replan: enabled (bounded by replan_max_iterations)
```

## 5. Agent State Model

### 5.1 State Types

| State Type | Persists | Across Restarts | Contents |
|-----------|----------|-----------------|----------|
| `stateless` | No | No | Nothing between invocations |
| `session` | During execution | No (lost on ABORT/COMPLETE) | Plan, tool history, intermediate outputs, variables |
| `checkpoint` | Yes (snapshot) | Yes (Mode 3 resume) | Full agent state serialized in snapshot |

## 6. Tool Invocation Within Agents

### 6.1 Invocation Path

```
Agent Orchestrator
       │
       │ agent decides: invoke(tool_X, inputs)
       │
       ▼
Agent Tool Proxy
       │
       ├── Validate: tool is in agent_contract.tool_allowlist
       ├── Validate: max_invocations not exceeded
       ├── Validate: scope = "full" or "restricted" (filter inputs/outputs)
       │
       ├── invoke(tool_X, filtered_inputs, agent_context)
       │         │
       │         ▼
       │   Tool Adapter (full pipeline: sandbox + provider + normalize)
       │         │
       │         ▼
       │   ToolResult
       │
       ├── Record in agent_state.tool_history
       ├── Aggregate result into agent_state.context
       │
       ▼
Agent Orchestrator (decide next action)
```

### 6.2 Tool Allowlist Enforcement

```
Before every tool invocation:

  1. Look up tool_ref in agent_contract.tool_allowlist
  2. If NOT found → FAIL invocation (tool not authorized for this agent)
  3. If found AND scope = "restricted":
     - Filter inputs to only declared input keys
     - Filter outputs to only declared output keys
  4. Increment invocation counter for this tool
  5. If counter > max_invocations → FAIL invocation (exceeded limit)
```

### 6.3 Aggregated Side Effects

```
The agent's side_effect_surface is the UNION of:
  - All tool side effects in its allowlist
  - Any declared agent-level side effects

This aggregated surface is used for wave conflict detection
by the Scheduler, just like individual tool surfaces.
```

| Condition | Result Status |
|-----------|---------------|

## 8. Agent Lifecycle

```
REGISTERED
    │
    ▼
VALIDATED              ← agent_contract.validation.self_check
    │
    ├── PASS ──► ADMITTED (via Governance Admission Controller)
    │              │
    │              ▼
    │            ACTIVE ──► serves invocations
    │              │
    │              ├── error_count > threshold ──► DEGRADED
    │              │                                 │
    │              │                                 ├── recover ──► ACTIVE
    │              │                                 │
    │              │                                 └── exhausted ──► DEACTIVATED
    │              │
    │              └── explicit unregister ──► DEACTIVATED
    │
    └── FAIL ──► REJECTED (terminal)
```

Identical lifecycle to tools (§8 of ADR-0003-D). Same validation gate, same degradation path, same monotonicity guarantee.

## 9. Agent Isolation

### 9.1 Nested Isolation Model

```
┌─────────────────────────────────────────────┐
│ AGENT ISOLATION BOUNDARY                     │
│                                              │
│  ┌──────────────────────────────┐            │
│  │ Agent Process/Container      │            │
│  │                              │            │
│  │  ┌──────────────────────┐    │            │
│  │  │ Tool Invocation 1    │    │            │
│  │  │ (sandboxed)          │    │            │
│  │  └──────────────────────┘    │            │
│  │                              │            │
│  │  ┌──────────────────────┐    │            │
│  │  │ Tool Invocation 2    │    │            │
│  │  │ (sandboxed)          │    │            │
│  │  └──────────────────────┘    │            │
│  │                              │            │
│  └──────────────────────────────┘            │
│                                              │
│  Agent filesystem access: scoped:<workspace> │
│  Agent network access:    restricted:<api>   │
└─────────────────────────────────────────────┘
```

Each tool invocation within an agent is individually sandboxed per the tool's own contract. The agent's isolation model is the outer boundary. The tool's isolation refines (narrows) within that boundary.

**Rule:** `agent.isolation ≥ tool.isolation` for every tool in allowlist. An agent in `process` isolation cannot invoke a tool requiring `container` isolation — this is validated at ADMITTED time by Governance.

## 10. Planning Engine

### 10.1 Plan Generation

Applicable only when `orchestration.model ∈ {"planned", "autonomous"}`.

```
PLAN_GENERATE(task, context, tool_allowlist):
  1. Agent receives the task description
  2. Agent calls LLM provider with:
     - Task description
     - Available tools (from allowlist) with their contracts
     - Current context (accumulated outputs, artifacts)
  3. LLM returns a plan: ordered list of tool invocations with inputs
  4. Plan is validated:
     - Every tool_ref is in allowlist
     - Every input matches tool contract
     - Plan depth ≤ agent_contract.plan.max_depth
  5. If validation fails → agent retries plan generation (up to 3 attempts)
     If exhausted → agent returns failure
```

### 10.2 Plan Execution

```
PLAN_EXECUTE(plan, agent_state):
  for each step in plan.steps (ordered):
    if step.status ≠ "pending":
      skip

    step.status ← "running"
    result ← TOOL_INVOKE(step.tool_ref, step.inputs, agent_context)
    step.result ← result

    if result.status = "success":
      step.status ← "success"
      aggregate(result.outputs → agent_state.context)

    else if result.status = "failure":
      step.status ← "failure"

      if orchestration.model = "autonomous" AND replan_enabled:
        replan_count ← REPLAN(from: step, reason: result.error)
        if replan_count ≤ replan_max_iterations:
          continue executing new plan tail
        else:
          return "failure"  # replan exhausted

      else:
        return "failure"    # planned model, no replan

  return "success"
```

### 10.3 Replan Algorithm

```
REPLAN(failed_step, error_context):
  1. Preserve completed steps (they remain SUCCESS)
  2. Discard pending steps
  3. Generate new plan tail from failed_step onward
  4. Validate new tail (same rules as initial plan)
  5. Replace plan tail with new tail
  6. Record replan event in agent_state.plan.replan_history
  7. Return updated plan
```

**Replan is bounded.** `replan_max_iterations` prevents infinite replan loops. After exhaustion, the agent returns `failure`.

## 12. Agent Handoff Model

When `agent_contract.handoff.next_agent` is set:

```yaml
agent_handoff:
  from_agent: "<agent-id>"
  to_agent: "<agent-ref>"
  pass_context:
    artifacts: ["<key>"]
    evidence: ["<key>"]
    variables: ["<key>"]
  reason: "<string>"
```

**Handoff protocol:**

```
1. FROM agent completes with status = "success"
2. AgentResult.handoff contains next_agent and pass_context
3. Commit Engine records AgentResult
4. Event Bus emits AgentHandoff event
5. TO agent's CEG node becomes eligible (if dependency edge exists)
6. TO agent receives pass_context as part of its invocation context
```

Handoff is a CEG-level concept — the dependency edge between agent nodes determines execution order. The `handoff` field in AgentResult is metadata that enables context passing at runtime.

## 13. Agent Failure Semantics

| Failure Type | Agent Result | Node Result | Tools Affected | Recovery |
|-------------|-------------|-------------|----------------|----------|
| Plan generation failed | `failure` | FAILED | None executed | Re-execute agent node |
| Tool failure (no replan) | `failure` | FAILED | Completed tools remain SUCCESS | Re-execute agent node |
| Tool failure (replan exhausted) | `failure` | FAILED | Completed tools remain SUCCESS | Re-execute agent node |
| Agent timeout | `timeout` | FAILED | Inflight tools killed | Re-execute agent node |
| Cancellation | `cancelled` | TERMINATED | Inflight tools cancelled | Resume if Mode 3 |
| Tool allowlist violation | `failure` | FAILED | Violation detected pre-invocation | Re-execute agent node |
| Max invocations exceeded | `failure` | FAILED | All prior tools recorded | Re-execute agent node |
| Output validation failed | `failure` | FAILED | All tools completed | Re-execute agent node |

**Key principle:** Tool failures within an agent do NOT cascade to other CEG nodes directly. Only the agent node's final status propagates through CEG dependency edges. Tools are internal to the agent's scope.

## 15. Integration Contracts

### 15.1 Agent Adapter ↔ Dispatcher

```
Dispatcher invokes:  AgentAdapter.invoke(agent_id, inputs, context)
Dispatcher receives: AgentResult
Dispatcher does:     Passes result to Commit Engine

Agent Adapter obeys:  All constraints in execution context
Agent Adapter enforces: Tool allowlist, max invocations, scope restrictions
Agent Adapter never:  Calls Governance, modifies CEG, commits node state
```

### 15.2 Agent Adapter ↔ Tool Pipeline

```
Agent invokes tools via:  Tool Adapter (same pipeline as capability nodes)
Agent enforces:            Tool allowlist, invocation limits, scope restrictions
Agent aggregates:          Tool results into agent_state.context

Agent never:  Bypasses the sandbox, invokes tools outside allowlist, exceeds limits
```

### 15.3 Agent Adapter ↔ Governance

```
Governance produces: CapabilityContract → includes agent-specific scope
Agent Adapter receives: CapabilityContract in execution context
Agent Adapter enforces: Tool allowlist already validated at admission time
Agent Adapter never:  Calls Governance during execution (GI-014)
```

### 15.4 Agent Adapter ↔ Commit Engine

```
Agent Adapter returns: AgentResult to Dispatcher
Dispatcher passes:     AgentResult to Commit Engine
Commit Engine:         Applies node state, journals result

Agent Adapter never:   Writes node state directly (RI-009)
```

## 18. Decision Outcome

Agent adapters are orchestrators that compose tool invocations into coherent execution sequences. They operate within a single CEG agent node, use the same tool pipeline as standalone capability nodes, enforce tool allowlists and invocation limits, and support three orchestration models (reactive, planned, autonomous). Agents have state (session, plan, tool history) scoped to their node execution. Replanning is bounded. Handoff enables context passing between agent nodes. All agent results normalize through the same Commit Engine pipeline. Agent isolation nests tool isolation within it. Agents never call Governance during execution — all capability enforcement is local.

---

## 19. Consequences

**Positive:**
- Unified tool invocation pipeline — agents and standalone capabilities use identical tool path
- Bounded replan prevents infinite loops while enabling autonomous recovery
- Tool allowlist provides fine-grained control over agent capabilities
- Agent handoff enables multi-agent workflows without breaking CEG semantics
- Agent state model supports session, planning, and checkpoint persistence
- Three orchestration models cover the full spectrum from simple Q&A to autonomous debugging

**Constraints:**
- Agent planning depends on LLM provider availability and quality
- Agent state is scoped to a single CEG node — cross-node state requires explicit handoff
- replan_max_iterations is a hard limit — complex tasks may exhaust it
- Agent isolation must be ≥ all tool isolations — may require container isolation for agents that use container-isolated tools
- No sub-agent spawning in v1 — multi-agent composition is at the CEG level
- Agent result is all-or-nothing: partial tool successes within a failed agent are recorded in agent_state but the node is FAILED

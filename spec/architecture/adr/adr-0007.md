# ADR-0007 — Formal Verification Bridge

**Status:** PROPOSED
**Depends on:** ADR-0004 (Observability), ADR-0005 (State Model), ADR-0006 (Consistency Controller)
**Layer:** Formal Methods — Verification Abstraction
**Scope:** Any execution with complete traces and/or snapshots (Mode 2 partial, Mode 3 full)

---

## 1. Core Thesis

```
ADR-0007 introduces a Formal Verification Bridge that translates
runtime artifacts (CEG, traces, snapshots, drift events) into a
mathematically analyzable state-transition system.

It does NOT execute runtime logic.
It does NOT replace ECCC (ADR-0006).
It does NOT re-implement the system.
It does NOT assign truth values to runtime states.

It constructs a Formal Execution Graph (FEG) — a loss-minimized
semantic abstraction of the execution — that enables external
provers (model checkers, SMT solvers, theorem provers) to reason
about correctness properties:

  - Safety:   nothing bad ever happens
  - Liveness:  something good eventually happens
  - Determinism: identical inputs → identical paths
  - Convergence: all paths reach terminal state
```

## 3. Formal Execution Graph (FEG)

### 3.1 Definition

```
FEG = (S, T, δ, s₀, F)

Where:
  S  = finite set of abstract system states
  T  = finite set of transition labels
  δ  = S × T → S  (deterministic transition function)
  s₀ ∈ S          (initial state)
  F  ⊆ S          (terminal/accepting states)

System class:
  determinism:      "deterministic"           # δ is a total function, not a relation
  state_space:      "bounded_finite"          # |S| ≤ |V_CEG| × |status_lattice| × |wave_count|
  concurrency:      "wave_synchronized"       # transitions within a wave are independent;
                                              # cross-wave transitions are totally ordered
```

### 3.3 Abstraction Mapping (Soundness Foundation)

The FEG is not an arbitrary model — it is a sound abstraction of the concrete execution.

```
Abstraction function:
  α: ConcreteExecution → FEG
  α maps every trace, commit event, and snapshot state to an FEG state
  and every commit sequence step to an FEG transition.

Concretization function:
  γ: FEG → ℘(ConcreteExecution)        (powerset — over-approximation)
  γ maps each FEG state to the set of all concrete execution states
  that are abstracted to that FEG state.
```

**Soundness condition (theorem obligation):**

```
∀ execution e:
  behaviors(e) ⊆ behaviors(γ(α(e)))

Where behaviors(x) is the set of all observable state sequences
in execution e or in any concrete execution compatible with FEG state x.

Meaning: Every behavior observed in the real execution is represented
in the FEG model. The FEG over-approximates reality — it may admit
behaviors that never occur, but it MUST NOT exclude behaviors that do occur.
```

**Soundness corollary — property preservation:**

```
If a safety property P holds for all behaviors in γ(α(e)):
  γ(α(e)) ⊨ P
Then P holds for the concrete execution:
  e ⊨ P

Proof: behaviors(e) ⊆ behaviors(γ(α(e))) and γ(α(e)) ⊨ P ⇒ e ⊨ P

This is the formal justification for FV-009.
```

### 3.2 State Abstraction

A system state in the FEG abstracts away implementation detail while preserving semantic equivalence.

```yaml
feg_state:
  state_id: "<uuid>"
  abstracted_from:
    execution_id: "<uuid>"
    wave_id: <int>
    trace_ids: ["<uuid>"]

  # Node status abstraction (per-node → abstract state component)
  node_vector:
    - node_id: "<uuid>"
      abstract_status: "NOT_STARTED" | "ACTIVE" | "TERMINAL_SUCCESS" |
                        "TERMINAL_FAILURE" | "TERMINAL_SKIPPED"
      dependency_closure_satisfied: true | false

  # Scheduler abstraction
  scheduler:
    phase: "INIT" | "WAVE_DISPATCH" | "WAVE_COMMIT" | "LAYER_COMPLETE" | "TERMINAL"
    active_nodes: <int>
    blocked_nodes: <int>

  # Global invariants (evaluated at each state)
  invariants:
    no_duplicate_execution: true | false
    dependency_closure_valid: true | false
    wave_boundary_consistent: true | false
```

### 3.3 Transition Abstraction

```yaml
feg_transition:
  transition_id: "<uuid>"
  label: "NODE_START" | "NODE_COMMIT" | "WAVE_COMPLETE" | "LAYER_COMPLETE" |
         "ESCALATE" | "TERMINATE" | "SNAPSHOT_CREATE" | "RECOVER"
  source_state: "<state_id>"
  target_state: "<state_id>"
  triggered_by:
    node_id: "<uuid>" | null
    trace_id: "<uuid>" | null
```

## 4. Semantic Extraction Layer

### 4.1 Purpose

Convert concrete runtime artifacts into the abstract FEG representation.

### 4.2 Extraction Pipeline

```
EXTRACT_FEG(execution_id, CEG, trace_set, snapshot_set, drift_set):
  1. BUILD initial state s₀ from CEG root nodes
  2. SORT traces by commit.sequence
  3. For each trace in order:
     a. MAP trace.commit → FEG transition
     b. COMPUTE resulting FEG state
     c. VALIDATE transition preserves invariants
     d. APPEND (state, transition) to FEG
  4. For each snapshot:
     a. MAP snapshot.status_map → FEG state at snapshot point
     b. VALIDATE snapshot state ≡ FEG state at corresponding wave
     c. If mismatch → emit EXTRACTION_WARNING (snapshot diverges from FEG)
  5. For each drift_event:
     a. ANNOTATE corresponding FEG transition with drift reference
  6. RETURN FEG
```

### 4.3 Mapping Rules

**Rule 1 — Node Execution:**

```
trace where trace.commit.terminal_status ∈ {SUCCESS, FAILURE, SKIPPED}
  → transition(label = NODE_COMMIT)
  → target state: node abstract_status updated
```

**Rule 2 — Wave Execution:**

```
set of traces from same wave (all committed)
  → after last trace in wave: transition(label = WAVE_COMPLETE)
  → target state: scheduler.phase updated
```

**Rule 3 — Snapshot State:**

```
snapshot at wave W
  → FEG state at the WAVE_COMPLETE transition for wave W-1
  → must be equivalent under state abstraction
```

**Rule 4 — Drift Annotation:**

```
drift_event referencing trace T
  → corresponding FEG transition annotated:
    feg_transition.drift_ref = drift_event.drift_id
  → invariant evaluated: does drift violate a safety property?
```

### 4.4 Abstraction is Loss-Minimized, Not Lossless

```
Some runtime details are abstracted away:
  - Exact tool inputs/outputs (abstracted to status + hash)
  - Agent replan history (abstracted to replan_count)
  - Timing (abstracted to sequence order)
  - Provider identities (abstracted to capability_ref)

What is PRESERVED:
  - Node execution order (commit sequence)
  - Terminal status of every node
  - Dependency graph satisfaction
  - Wave/layer progression
  - Invariant violations (via drift annotations)
  - Snapshot consistency (via extraction warnings)
```

## 5. Verification Properties

### 5.1 Safety Properties

```
"Nothing bad ever happens"

Expressible as LTL/CTL formulas over FEG states and transitions.

Examples:
  □ (node.executing → dependency_closure_satisfied)
     "A node never executes before its dependencies are satisfied"

  □ (node.terminal → ¬◇ node.executing)
     "A terminal node never executes again"

  □ (scheduler.phase = WAVE_DISPATCH → all active nodes are conflict-free)
     "Wave dispatch never includes conflicting nodes"
```

### 5.2 Liveness Properties

```
"Something good eventually happens"

  ◇□ (∃ READY nodes → ◇ scheduler.phase = WAVE_DISPATCH)
     "If ready nodes exist, a wave dispatch eventually occurs"

  □ (node.executing → ◇ node.terminal)
     "Every executing node eventually reaches a terminal state"

  □ (scheduler.phase = INIT → ◇ scheduler.phase = TERMINAL)
     "Execution eventually completes (no infinite loops)"
```

### 5.3 Determinism Property

```
"Identical inputs produce identical FEG paths"

For any two executions E₁, E₂ with:
  - Same RIR (rir_hash match)
  - Same runtime fingerprint
  - Same provider determinism constraints (ADR-0004 §6.3)

Then:
  FEG(E₁) ≅ FEG(E₂)
  (graph isomorphism under state abstraction)
```

### 5.4 Convergence Property

```
"All execution paths converge"

  All maximal paths in FEG eventually reach a state in F (terminal).
  There is no infinite path that avoids F.
  The FEG is a DAG — guaranteed by CEG construction (ADR-0002-B).
```

### 5.5 Expressiveness Boundary — What FEG CANNOT Prove

The FEG is a structural abstraction. It proves properties about execution ORDER, STATE TRANSITIONS, and DEPENDENCY SATISFACTION. It does NOT prove properties about the semantic CONTENT of execution outputs.

```
VERIFIABLE (within FEG):

  ✓ Node execution order respects dependency graph
  ✓ No duplicate execution of any node
  ✓ All nodes eventually reach terminal state
  ✓ Wave/layer progression is monotonic
  ✓ Snapshot state is consistent with trace projection
  ✓ Replay produces identical FEG under deterministic constraints
  ✓ Commit sequence is gap-free and total

NON-VERIFIABLE (outside FEG scope):

  ✗ Semantic correctness of tool outputs (is the file content correct?)
  ✗ Probabilistic model behavior (LLM sampling with temperature > 0)
  ✗ External system effects (did the API call actually mutate production?)
  ✗ Real-world I/O truthfulness (does fs/write contain valid data?)
  ✗ Cross-execution semantic equivalence (do two different executions
    produce semantically equivalent results?)
  ✗ Time-dependent race conditions (if wave barrier is violated by a bug)
```

**Rule:**

```
ADR-0007 proves STRUCTURAL CORRECTNESS of the execution system.
It does NOT prove SEMANTIC CORRECTNESS of execution outputs.

Structural correctness = the system executed what it said it would,
in the order it said it would, with the dependencies it declared.

Semantic correctness = the outputs are factually correct.
This requires external validation (human review, integration tests,
formal specification of output semantics — out of scope for v1).
```

This boundary is critical. Without it, users may falsely assume that a "verified" execution produced correct outputs, when only the execution STRUCTURE was verified.

## 7. Relationship to ADR-0006 (ECCC)

ADR-0006 and ADR-0007 address fundamentally different questions:

| Dimension | ADR-0006 (ECCC) | ADR-0007 (FVB) |
|-----------|-----------------|----------------|
| **Question** | "Did something differ?" | "Could something ever go wrong?" |
| **Method** | Structural differential comparison | Formal model construction + proof |
| **Input** | Traces + snapshots | FEG (derived from traces + snapshots + CEG) |
| **Output** | DRIFT_EVENT (structural diff) | Verification Report (proof pass/fail) |
| **Scope** | Post-facto (after execution) | Post-facto + a priori (property holds for all possible executions) |
| **Consumes** | Runtime artifacts directly | FEG abstraction of runtime artifacts |
| **Authoritative** | No — drift detection only | No — proof only, no enforcement |

**ADR-0006 feeds ADR-0007:**
- Drift events annotate FEG transitions
- A structurally sound execution (no drift) is a prerequisite for formal verification
- Drift on a trace makes any FEG containing that trace INVALID for proof purposes

## 10. Critical Design Constraint

```
ADR-0007 MUST NOT:

  ✗ Execute runtime logic
  ✗ Validate or classify drift (ADR-0006 owns that)
  ✗ Modify snapshots, traces, or CEG
  ✗ Depend on runtime timing or wall-clock
  ✗ Assign severity to any divergence
  ✗ Enforce policy or trigger remediation
  ✗ Replace or duplicate the ECCC

It ONLY:

  ✓ Constructs formal model from completed runtime artifacts
  ✓ Emits verification artifacts consumable by external provers
  ✓ Preserves semantic equivalence under abstraction
  ✓ Annotates FEG with drift references (pass-through from ADR-0006)
```

## 13. Decision Outcome

ADR-0007 introduces the Formal Verification Bridge — a semantic extraction layer that converts runtime artifacts (CEG, traces, snapshots, drift events) into a Formal Execution Graph (FEG), a deterministic, wave-synchronized, bounded-finite state-transition system. The FEG is a sound abstraction of the concrete execution via α/γ mapping (behaviors(e) ⊆ behaviors(γ(α(e)))), guaranteeing that properties proved on the FEG hold for the real execution. The FEG preserves execution order, terminal status, dependency satisfaction, and invariant annotations. The Verification Contract packages the FEG with target properties (safety, liveness, determinism, convergence) and proof targets for external provers (model checkers, SMT solvers, theorem provers). The bridge proves STRUCTURAL correctness (execution structure, order, dependencies) — it does NOT prove SEMANTIC correctness of outputs. The expressiveness boundary is explicitly declared. The bridge never executes runtime logic, never modifies state, and never duplicates ADR-0006.

## 14. Consequences

**Positive:**
- System becomes mathematically analyzable — safety, liveness, determinism, and convergence are provable
- FEG enables external verification without exposing runtime internals
- Verification Contract is a standardized interface for any prover (model checker, SMT, theorem prover)
- Drift annotations in FEG link structural issues to formal property violations
- Sound abstraction guarantees: properties proved on FEG hold for concrete execution
- Opens path to safety-critical deployment and verified AI execution

**Constraints:**
- FEG construction cost is O(n²) in worst case (state count grows with trace count)
- Abstraction is sound (α/γ) but not bisimilar — FEG over-approximates, admitting behaviors that never occur
- FEG proves STRUCTURAL correctness only — semantic correctness of outputs is outside scope (§5.5)
- Some runtime behaviors (LLM stochastic outputs) have no deterministic formal model and require abstraction to "nondeterministic choice" which may weaken provable properties
- External prover integration is tool-specific — no universal proof format in v1
- Verification is post-facto — it does not prevent errors, only proves their absence in the model
- Soundness depends on correct α/γ construction — if the mapping is buggy, proofs are vacuously true

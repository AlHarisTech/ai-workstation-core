# ADR-0003-D — Tool Adapters

**Status:** PROPOSED
**Depends on:** ADR-0003-B (Runtime Engine), ADR-0003-E (Governance Engine), ADR-0002-E (Plugin Architecture)
**Layer:** Runtime Core — Execution Adapters
**Scope:** Mode 2 / Mode 3. Mode 0/1 are bypass paths.

---

## 1. Core Thesis

```
A Tool Adapter is the runtime binding between a CEG capability node
and an external execution primitive (CLI, API, LLM provider, MCP server,
database, filesystem operation).

Every tool invocation flows through the Dispatcher (ADR-0003-B §4.3).
The Dispatcher enforces the CapabilityContract (ADR-0003-E §4.4) locally.
No tool adapter interacts with Governance at execution time.

Tool adapters are STATELESS between invocations.
No retained context. No session affinity. No warm caches that affect results.
```

---

## 2. Tool Position in the Execution Stack

```
CEG Capability Node (type: capability)
       │
       ▼
Dispatcher.resolve()
       │
       ▼
Tool Adapter
       │
       ├── Isolation Binder (enforce sandbox)
       ├── Capability Contract (local enforcement)
       ├── Provider Resolver (select backend)
       └── Invocation (execute + timeout + capture)
       │
       ▼
Result Normalizer
       │
       ▼
Commit Engine
```

## 3. Tool Contract

Every tool adapter MUST declare its contract before it can be loaded.

```yaml
tool_contract:
  tool_id: "<uuid>"
  name: "<string>"
  version: "<semver>"

  # What this tool provides
  capability_ref: "<capability-ref>"      # maps to governance capability namespace

  # Execution properties
  execution:
    model: "synchronous" | "async_poll"
    timeout_ms: <int>                      # max wall-clock time
    idempotent: true | false               # same inputs → same outputs
    retry:
      max_attempts: <int>
      backoff: "constant" | "linear" | "exponential"

  # Input/Output contract
  inputs:
    - name: "<string>"
      type: "<type>"
      required: true | false
      default: "<value>" | null
      description: "<string>"

  outputs:
    - name: "<string>"
      type: "<type>"
      description: "<string>"

  # Side effect declaration (CRITICAL — used for wave conflict detection)
  side_effect_surface:
    - "fs:<path>"                          # filesystem access surface
    - "network:<domain>"                   # network access surface
    - "db:<resource>"                      # database access surface
    - "none"                               # no side effects

  # Provider binding
  provider:
    type: "llm" | "mcp_server" | "cli" | "api" | "internal"
    config_ref: "<provider-config-ref>"

  # Isolation requirements
  isolation:
    model: "process" | "container" | "virtual" | "inline"
    filesystem_access: "none" | "read_only:<path>" | "scoped:<path>"
    network_access: "none" | "restricted:<domain-list>" | "full"
    memory_limit_mb: <int>
    cpu_limit: "<cgroup-spec>" | null

  # Validation
  validation:
    self_check:
      command: "<string>"
      expected_output: "<regex>" | null
      timeout_ms: <int>
```

## 4. Provider Abstraction

### 4.1 Provider Model

Providers abstract the backend that executes a tool. A single tool may be bound to one or more providers. The provider is resolved at dispatch time based on the execution context.

```yaml
provider_config:
  provider_id: "<uuid>"
  type: "llm" | "mcp_server" | "cli" | "api" | "internal"

  # Provider-specific configuration
  llm:
    backend: "openai" | "anthropic" | "gemini" | "openrouter" | "local"
    model: "<model-id>"
    api_base_url: "<url>" | null
    max_tokens: <int>

  mcp_server:
    transport: "stdio" | "sse" | "websocket"
    command: "<string>" | null            # for stdio transport
    url: "<url>" | null                   # for sse/websocket transport
    env: { "<key>": "<value>" }

  cli:
    command: "<string>"
    args: ["<arg>"]
    env: { "<key>": "<value>" }
    working_dir: "<path>" | null

  api:
    base_url: "<url>"
    method: "GET" | "POST" | "PUT" | "DELETE"
    headers: { "<key>": "<value>" }
    auth:
      type: "bearer" | "api_key" | "basic" | "none"
      credential_ref: "<credential-ref>"  # resolved by credential manager, NEVER inlined

  internal:
    handler: "<function-ref>"             # in-process handler for trivial operations

  # Credential management
  credentials:
    source: "env" | "vault" | "governance"
    key_ref: "<credential-ref>"           # reference ONLY — never inline secrets

  # Health
  health_check:
    endpoint: "<url>" | null
    interval_ms: <int>
    timeout_ms: <int>
```

### 4.2 Provider Lifecycle

```
REGISTERED
    │
    ▼
HEALTH_CHECK
    │
    ├── HEALTHY ──► ACTIVE
    │
    └── UNHEALTHY ──► DEGRADED
                        │
                        ├── retry N times ──► HEALTHY ──► ACTIVE
                        │
                        └── exhausted ──► UNAVAILABLE
                                            │
                                            ▼
                                    All tool invocations using this provider → FAILED
```

**Rule:** Provider health is checked at plugin load time and periodically (per `health_check.interval_ms`). An UNAVAILABLE provider causes all bound tool invocations to fail immediately — no retry, no queue.

## 6. Tool Sandbox

### 6.1 Sandbox Model

The sandbox is enforced by the Isolation Binder sub-component of the Dispatcher BEFORE provider invocation.

```yaml
sandbox_spec:
  model: "process" | "container" | "virtual" | "inline"

  # process = separate OS process, seccomp/apparmor
  # container = OCI container (Docker/Podman)
  # virtual = microVM (Firecracker)
  # inline = in-process (no isolation — only for idempotent, side-effect-free tools)

  filesystem:
    root: "<path>"                        # sandbox root
    writable: ["<path>"]                  # paths writable within sandbox
    read_only: ["<path>"]                 # paths readable within sandbox
    hidden: ["<path>"]                    # paths invisible within sandbox

  network:
    egress: "none" | "restricted:domains" | "full"
    allowed_domains: ["<domain>"]
    dns_resolution: true | false

  resources:
    max_memory_mb: <int>
    max_cpu_percent: <int>
    max_disk_mb: <int>
    max_processes: <int>

  timeouts:
    execution_timeout_ms: <int>           # wall-clock
    idle_timeout_ms: <int>               # no output for this duration
```

### 6.2 Sandbox Violation

| Violation | Detection | Action |
|-----------|-----------|--------|
| Filesystem access outside allowed paths | seccomp trap / ptrace | KILL + result = `sandbox_violation` |
| Network access outside allowed domains | egress filter | KILL + result = `sandbox_violation` |
| Memory limit exceeded | cgroup OOM | KILL + result = `sandbox_violation` |
| CPU time exceeded | cgroup CPU limit | KILL + result = `timeout` |
| Execution timeout | wall-clock timer | SIGKILL + result = `timeout` |
| Process count exceeded | cgroup pids | KILL + result = `sandbox_violation` |

**All sandbox violations result in the node being marked FAILED (not SKIPPED).** The violation is recorded in the audit trail.

## 7. Tool Result Normalization

The Result Normalizer sub-component of the Dispatcher converts raw provider output into a canonical `ToolResult`.

### 7.1 Normalization by Provider Type

| Provider Type | Success Condition | Failure Condition |
|---------------|-------------------|-------------------|
| `llm` | HTTP 200 + valid JSON response body | HTTP error, parse error, content filter |
| `mcp_server` | MCP response without error | MCP error response, connection lost |
| `cli` | Exit code 0 | Non-zero exit code, timeout, signal |
| `api` | HTTP 2xx | HTTP 4xx/5xx, connection error, timeout |
| `internal` | Return value without exception | Exception thrown |

### 7.2 Normalization Rules

```
NORMALIZE(raw_output, tool_contract, invocation):

  1. If timeout_kill applied:         → status = "timeout"
  2. If sandbox_violation detected:   → status = "sandbox_violation"
  3. If cancelled during invocation:  → status = "cancelled"
  4. If provider returned error:      → status = "failure" + error details
  5. If provider returned success:    → status = "success" + map outputs per contract
  6. Attach metrics (duration, tokens, bytes)
  7. Attach sandbox audit (observed filesystem/network accesses)
```

## 8. Tool Lifecycle

```
REGISTERED
    │
    ▼
VALIDATED              ← tool_contract.validation.self_check
    │
    ├── PASS ──► ADMITTED (via Governance Admission Controller)
    │              │
    │              ▼
    │            ACTIVE ──► serves invocations
    │              │
    │              ├── error_count > threshold ──► DEGRADED
    │              │                                 │
    │              │                                 ├── recover ──► ACTIVE
    │              │                                 │
    │              │                                 └── exhausted ──► DEACTIVATED
    │              │
    │              └── explicit unregister ──► DEACTIVATED
    │
    └── FAIL ──► REJECTED (terminal)
```

**Lifecycle rules:**
- VALIDATED → REJECTED is terminal for this tool version.
- DEGRADED allows invocations but with a warning annotation in the result.
- DEACTIVATED means no new invocations; inflight invocations complete.
- A tool in DEACTIVATED causes its CEG capability nodes to be marked FAILED if they haven't started yet.

## 9. Tool Retry Model

### 9.1 When Retry Applies

```
RETRY is attempted ONLY when:
  - status = "failure" (provider error)
  - AND tool_contract.execution.retry is configured
  - AND max_attempts not exhausted
  - AND failure is transient (connection error, rate limit, 5xx)

RETRY is NOT attempted when:
  - status = "success"      (already succeeded)
  - status = "timeout"      (retry would double execution time)
  - status = "cancelled"    (explicit cancellation)
  - status = "sandbox_violation"  (security violation, not instability)
  - tool marked idempotent = false AND failure was partial (side effects may have occurred)
```

### 9.2 Retry Backoff

```yaml
retry_result:
  attempt: <int>
  max_attempts: <int>
  backoff_ms: <int>                      # current backoff duration
  next_retry_at: "<iso8601>" | null
  status: "retrying" | "exhausted" | "success"
```

**Backoff calculation:**
- `constant`: backoff_ms = fixed value per attempt
- `linear`: backoff_ms = base * attempt
- `exponential`: backoff_ms = base * (2 ^ (attempt - 1))

## 10. Tool Failure Semantics

| Failure Type | Tool Result Status | Node Result | Plugin State | Notes |
|-------------|-------------------|-------------|--------------|-------|
| Provider unavailable | `failure` | FAILED | ACTIVE | All subsequent invocations also FAIL |
| Execution timeout | `timeout` | FAILED | ACTIVE | Retry not attempted |
| Sandbox violation | `sandbox_violation` | FAILED | DEGRADED | Security event recorded |
| Invalid inputs | `failure` | FAILED | ACTIVE | Schema validation error — no retry |
| Provider error (transient) | `failure` | FAILED | ACTIVE | Retry per policy |
| Provider error (permanent) | `failure` | FAILED | ACTIVE | No retry after exhaust |
| Cancellation | `cancelled` | TERMINATED | ACTIVE | Coordinator-initiated |
| Output validation failure | `failure` | FAILED | ACTIVE | Output did not match contract |

## 12. Integration Contracts

### 12.1 Tool Adapter ↔ Dispatcher

```
Dispatcher invokes:  ToolAdapter.invoke(tool_id, inputs, context)
Dispatcher receives: ToolResult
Dispatcher does:     Passes result to Commit Engine

Tool Adapter obeys:  All constraints in context (filesystem_scope, network_scope, timeout_ms)
Tool Adapter enforces: Sandbox isolation per tool_contract.isolation
Tool Adapter never:  Calls Governance, modifies CEG, commits node state
```

### 12.2 Tool Adapter ↔ Governance

```
Governance produces: CapabilityContract → includes tool-specific scope limits
Tool Adapter receives: CapabilityContract embedded in execution context
Tool Adapter enforces: Scope limits at sandbox boundary
Tool Adapter never:   Calls Governance API during invocation (GI-014)
```

### 12.3 Tool Adapter ↔ Commit Engine

```
Tool Adapter returns:  ToolResult to Dispatcher
Dispatcher passes:     ToolResult to Commit Engine
Commit Engine:         Validates transition, applies node state, journals result
Tool Adapter never:    Writes node state directly (RI-009)
```

## 14. Custom Tool Loading (Plugin-Based)

Custom tools follow the plugin contract from ADR-0002-E §4.3:

```
1. Tool plugin declares tool_contract in its manifest
2. Plugin Registry validates the contract (self_check)
3. Governance validates capability compatibility
4. Plugin is loaded in isolation (process/container)
5. Tool is registered in Tool Registry
6. Invocations flow through the standard Dispatcher pipeline
```

## 15. Invariants

| ID | Invariant | Enforced By |
|----|-----------|-------------|
| TI-001 | Every tool invocation is isolated per declared sandbox model | Isolation Binder |
| TI-002 | CapabilityContract constraints are enforced locally — no governance call during invocation | Tool Adapter |
| TI-003 | Tool result flows through Commit Engine — tool adapters never write node state | Dispatcher → Commit Engine |
| TI-004 | Side effects are declared in tool_contract and used for wave conflict detection | Tool Contract + Scheduler |
| TI-005 | Provider credentials are referenced, never inlined in contracts | Provider Config |
| TI-006 | Sandbox violations produce FAILED node state, not SKIPPED | Tool Adapter |
| TI-007 | Tool adapters are stateless between invocations | All tool adapters |
| TI-008 | Retry is bounded by max_attempts and backoff | Tool Adapter |
| TI-009 | Tools operate within provider type semantics — an `llm` tool cannot masquerade as `cli` | Provider Resolver |
| TI-010 | Provider health failure cascades to all bound tools | Provider Registry |
| TI-011 | Tool output must match declared contract schema — mismatch = FAILED | Result Normalizer |
| TI-012 | Tool lifecycle transitions are monotonic (ACTIVE → DEGRADED → DEACTIVATED; never reverse without re-registration) | Tool Registry |

## 17. Decision Outcome

Tool adapters are the primitive execution unit in the Runtime Engine. They are stateless, sandbox-isolated, and operate through a provider abstraction. Every invocation flows through the Dispatcher → Tool Adapter → Result Normalizer → Commit Engine pipeline. CapabilityContracts from Governance are enforced locally at the sandbox boundary. Tool side effects are declared in the contract and used for wave conflict detection. Provider health is monitored. Tool lifecycle is monotonic. All tool state transitions flow through the Commit Engine.

---

## 18. Consequences

**Positive:**
- Unified invocation model across all provider types (LLM, MCP, CLI, API, internal)
- Sandbox isolation enforced uniformly — no tool can exceed its declared scope
- CapabilityContract enforcement is local and synchronous — no governance latency at invocation time
- Side effect declarations enable deterministic parallel scheduling
- Provider health monitoring prevents cascading failures
- Built-in tool catalog covers common operations without external dependencies

**Constraints:**
- Tool adapters are stateless — no session affinity, no warm caches that affect determinism
- Provider UNAVAILABLE means all bound tools fail — execution may halt
- Streaming outputs not supported in v1
- Dynamic provider selection not supported in v1
- No tool-to-tool composition — agents orchestrate sequences

# ADR-0003-B — Runtime Engine Implementation

**Status:** PROPOSED
**Depends on:** ADR-0003-A (Execution Semantics & Concurrency)
**Layer:** Runtime Core — Mode 2 / Mode 3
**Scope:** Component-level specification of the Runtime Engine. Mode 0/1 are bypass paths and are not governed by this document.

---

## 1. Core Thesis

The Runtime Engine consumes a frozen RIR (containing CEG + execution_plan) and drives every node from PENDING to a terminal state through a set of cooperating components connected by an internal Event Bus. No component mutates the CEG. No component reinterprets spec semantics. The engine is a pure state-transition machine over a compile-time-validated graph.

---

## 2. Architectural Separation: Node State vs Runtime State

ADR-0003-A defined the **Node Status Lattice**:

```
PENDING | BLOCKED | READY | RUNNING | SUCCESS | FAILURE | SKIPPED | TERMINATED
```

This ADR adds an orthogonal **Runtime State Machine**:

```
RUNNING → TERMINATING → TERMINATED
RUNNING → ABORTED
```

| Dimension | Owned By | Meaning |
|-----------|----------|---------|
| Node State | Commit Engine | Outcome of a single execution unit (sole writer of all node status transitions) |
| Runtime State | Runtime Coordinator | Health and lifecycle of the engine itself |

**TERMINATED** is a node outcome (external stop signal). **ABORTED** is a runtime outcome (internal integrity failure). They live at different levels and MUST NOT be conflated.

## 4. Component Specifications

### 4.1 Runtime Coordinator

```
run(execution_plan) → ExecutionOutcome
terminate(reason)   → void
abort(reason)       → void        # immediate, no cleanup beyond kill signals
resume(snapshot_id) → ExecutionOutcome   # Mode 3 only
escalate()          → void               # triggers terminate → restart pipeline
```

**State-changing operations:**

| Operation | Trigger | Effect |
|-----------|---------|--------|
| **RUN** | Router dispatches Mode 2/3 execution | Initializes all components, starts scheduler loop |
| **RESUME** | Router dispatches Mode 3 with snapshot_id | Restores snapshot, resumes from next wave |
| **TERMINATE** | ESCALATE gate branch fires, or external shutdown | Drains current wave, sets non-terminal nodes → TERMINATED, emits context_snapshot |
| **ABORT** | Invariant violation, corrupted state, internal error | Stops immediately, flushes journal, no snapshot, manual investigation required |
| **ESCALATE** | Gate `target = "ESCALATE"` evaluated true | Calls `terminate(MODE_INSUFFICIENT)`, returns to Router for reclassify (F-004) |

**State machine:**

```
                    ┌─────────┐
                    │ CREATED │
                    └────┬────┘
                         │ run()
                    ┌────▼────┐
              ┌─────│ RUNNING │──────────────────────┐
              │     └────┬────┘                      │
              │          │                           │
              │   ┌──────┼──────┐            ┌───────▼──────┐
              │   │      │      │ abort()    │              │
              │   │      │      ├───────────►│   ABORTED    │
              │   │      │      │            │ (terminal)   │
              │   │      │      │            └──────────────┘
              │   │      │      │
              │   │  escalate()│
              │   │  terminate()│
              │   │      │      │
              │   │ ┌────▼──────────┐
              │   │ │ TERMINATING   │
              │   │ │ (drain waves) │
              │   │ └────┬──────────┘
              │   │      │
              │   │ ┌────▼──────┐
              │   └►│TERMINATED │────► Router (reclassify, F-004)
              │     └───────────┘
              │
              │ natural completion
              │
              └────► COMPLETED (terminal)
```

**Constraints:**
- The Coordinator orchestrates lifecycle decisions (RUN, TERMINATE, ABORT, RESUME, ESCALATE) but never writes node state directly. All node state transitions flow through the Commit Engine.
- `abort()` does NOT attempt graceful plugin teardown. It records ABORTED and stops.
- `terminate()` drains the current wave (completes in-flight dispatches), issues `TerminateRequest` to the Commit Engine for all non-terminal nodes, then (after Commit Engine processes) emits `context_snapshot` to the Router.
- `escalate()` calls `terminate(MODE_INSUFFICIENT)`, then emits `context_snapshot` to the Router.

### 4.2 Scheduler

```
claim(wave)              → [Node]       # select READY nodes for dispatch, issue DispatchClaim to Commit Engine
recompute()              → void         # evaluate BLOCKED → READY after commit (writes READY/SKIPPED via Commit Engine)
dispatch_wave(wave)      → void         # send wave to Dispatcher
```

**Sub-components:**

| Sub-component | Responsibility |
|---------------|---------------|
| **Lane Engine** | Iterates topological layers in order; computes lane boundaries per §5 (Concurrency Model, ADR-0003-A) |
| **Wave Dispatcher** | Partitions each lane into conflict-free waves (graph coloring, node-id-ordered); claims waves atomically |
| **Deadline Manager** | Tracks per-node `scheduling.deadline`; raises warning on proximity, escalates on expiry (if gate `ESCALATE` declared) |

**Algorithm:**

```
SCHEDULER_LOOP(execution_plan):
  for each lane ℓ in topological layer order:
    for each wave w in lane[ℓ].waves (ascending wave-index):
      ready_nodes ← claim(w)
      dispatch_wave(ready_nodes)        # parallel dispatch
      wait_for_wave_completion(w)
    recompute()                         # update BLOCKED → READY for next layer
```

**`recompute()` rules:**

```
For each node v where v.status ∈ {BLOCKED}:
  if all v.activation.requires ⊆ {SUCCESS}:
    if v.activation.condition evaluates TRUE:
      v.status ← READY
    else:
      v.status ← SKIPPED                  # activation permanently unsatisfiable
  else if any v.activation.requires ∩ {FAILURE} ≠ ∅:
    v.status ← SKIPPED                    # required predecessor failed
```

**Constraints:**
- `claim()` selects READY nodes and issues `DispatchClaim` events to the Commit Engine. The Commit Engine performs the actual `READY → RUNNING` transition. No node is claimed twice.
- `recompute()` evaluates `BLOCKED → READY` and `BLOCKED → SKIPPED`, issuing transitions through the Commit Engine. Called exactly once per layer, after all waves in that layer are terminal.
- Scheduler never invokes Dispatcher directly; it places nodes in a `ready_queue` that the Coordinator reads.
- Scheduler subscribes to `NodeCommitted` events on the Event Bus to trigger `recompute()`.
- The Scheduler's `runnable_set` is immutable between committed events (RI-020). No concurrent recomputation may produce a different READY set within the same wave epoch.

### 4.3 Adapter Dispatcher

```
resolve(unit)             → PluginInstance
execute(unit, context)    → ExecutionResult
cancel(unit_id)           → void            # best-effort
```

**Sub-components:**

| Sub-component | Responsibility |
|---------------|---------------|
| **Plugin Resolver** | Maps `unit.binding.contract` → concrete plugin instance; validates plugin is ACTIVE; enforces compatibility_mode |
| **Isolation Binder** | Pre-execution check: `plugin.isolation ≥ unit.region.isolation_requirement`; applies filesystem/network scoping |
| **Result Normalizer** | Converts raw plugin output → normalized `ExecutionResult` per unit type (agent/capability/task/gate/checkpoint) |

**Dispatch protocol:**

```
DISPATCH(unit, context):
  plugin ← resolve(unit.type, unit.binding.contract)

  # Pre-execution isolation check (compile-time guarantee, verified here)
  if plugin.isolation < unit.region.isolation_requirement:
    return ExecutionResult(CRITICAL_ISOLATION_MISMATCH)   # should never fire

  # Spawn
  result ← plugin.execute(unit, context)

  # Normalize
  normalized ← NORMALIZE(result, unit.type)
  return normalized
```

**Result normalization (per unit type):**

| Unit Type | Success Condition | Failure Condition |
|-----------|-------------------|-------------------|
| agent | `result.status == "success"` | any other status |
| capability | `result.status == "success"` | any other status |
| task | all sub-units SUCCESS | any sub-unit FAILURE |
| gate | condition evaluated (no execution) | predicate evaluation error |
| checkpoint | snapshot persisted (Mode 3) | persistence failure |

**Constraints:**
- Dispatcher enforces `plugin.timeout_ms`. Exceeded timeout → KILL_PLUGIN → FAILURE.
- Dispatcher enforces `plugin.isolation` at process boundary. Violation → KILL_PLUGIN → FAILURE.
- `cancel()` is best-effort only. Node state is set to TERMINATED immediately regardless of whether the plugin process actually stops.
- Every dispatch result flows through normalization before reaching Commit Engine.

### 4.4 Commit Engine

```
commit(node_id, result)   → void
publish(event)             → void
```

**Sub-components:**

| Sub-component | Responsibility |
|---------------|---------------|
| **Atomic State Commit** | Validates transition, acquires node lock, applies new status/outputs/artifacts/evidence, unlocks |
| **Event Publisher** | Publishes `NodeCommitted` to Event Bus AFTER journal write confirms durable |
| **Duplicate Commit Guard** | Detects and rejects repeat commits on already-terminal nodes (WARNING, not ABORT) |

**Commit protocol:**

```
COMMIT(node_id, result):
  # 1. Acquire node lock
  lock(node_id)

  # 2. Validate transition
  if not VALID_TRANSITION(node.status, result.status):
    unlock(node_id)
    ABORT_RUNTIME("INVALID_TRANSITION", node_id, node.status, result.status)

  # 3. Apply state
  node.status ← result.status
  node.outputs ← result.outputs
  node.artifacts ← result.artifacts
  node.evidence ← result.evidence

  # 4. Unlock
  unlock(node_id)

  # 5. Publish event
  publish(NodeCommitted(node_id, result.status))
```

**Valid transitions (ALL through Commit Engine):**

```
READY    → RUNNING     (Commit Engine, on DispatchClaim from Scheduler)
RUNNING  → SUCCESS     (Commit Engine, on ExecutionResult from Dispatcher)
RUNNING  → FAILURE     (Commit Engine, on ExecutionResult from Dispatcher)
READY    → TERMINATED  (Commit Engine, on TerminateRequest from Coordinator)
BLOCKED  → TERMINATED  (Commit Engine, on TerminateRequest from Coordinator)
RUNNING  → TERMINATED  (Commit Engine, on TerminateRequest from Coordinator)
PENDING  → TERMINATED  (Commit Engine, on TerminateRequest from Coordinator)
BLOCKED  → READY       (Commit Engine, on recompute from Scheduler)
BLOCKED  → SKIPPED     (Commit Engine, on recompute from Scheduler)
```

**Constraints:**
- Commit Engine publishes to Event Bus AFTER the commit is durable (journaled), per RI-016.
- If Event Bus publication fails after durable journal write: the event is marked `pending_publication` in the journal and the runtime enters ABORT. This prevents silent state drift where committed state exists in the journal but consumers never received the event.
- Double-commit detection: if node.status is already terminal, second commit is rejected with WARNING (not ABORT — no integrity loss).
- Commit Engine never invokes Scheduler directly. Scheduler reacts to `NodeCommitted` events on the Event Bus (RI-002).
- All transitions are monotonic — no node reverts from terminal to non-terminal (RI-004).

### 4.5 Event Bus

```
publish(event)     → void
subscribe(pattern) → Subscription
```

**Sub-components:**

| Sub-component | Responsibility |
|---------------|---------------|
| **Ordered Delivery** | Monotonic sequence number per event; in-order fan-out to all matching subscribers |
| **Consumer Registration** | Pattern-based subscription; slow-consumer detection and disconnection |

**Event schema:**

```yaml
event:
  event_id: "<uuid>"
  event_type: "NodeStarted" | "NodeCommitted" | "NodeFailed" |
              "NodeTerminated" | "NodeSkipped" |
              "WaveCompleted" | "LayerCompleted" |
              "CheckpointCreated" | "SnapshotRestored" |
              "EscalationRaised" |
              "RuntimeTerminated" | "RuntimeAborted" | "RuntimeCompleted"
  timestamp: "<iso8601>"
  payload:
    node_id: "<uuid>" | null
    status: "<node-status>" | null
    metadata: {}
```

**Constraints:**
- Events are ordered within a single execution (monotonic sequence number).
- Events are transient — the Event Bus does not persist. The Execution Journal persists.
- Subscribers receive events in order. No subscriber may block the bus — slow consumers are disconnected.
- The Event Bus is internal to the Runtime Engine. External systems consume the Execution Journal, not the Event Bus.

---

### 4.6 Execution Journal

```
append(event)   → void
replay(from, to)→ [Event]
```

**Purpose:** Durable, append-only audit record of every externally visible state transition.

**Schema (per entry):**

```yaml
journal_entry:
  sequence: <uint64>             # monotonic, gap-free
  event: <Event>                 # same schema as Event Bus
  durable: true                  # written before event publication
```

**Rule (RI-016):**

```
Every externally visible state transition
MUST be journaled BEFORE publication on the Event Bus.

Order:
  1. Append to Journal
  2. Journal confirms durable write
  3. Publish to Event Bus
```

**Externally visible transitions:**
- NodeStarted, NodeCommitted, NodeFailed, NodeTerminated, NodeSkipped
- EscalationRaised
- RuntimeTerminated, RuntimeAborted, RuntimeCompleted
- CheckpointCreated, SnapshotRestored

**NOT journaled (internal only):**
- BLOCKED → READY (internal Scheduler computation)
- WaveCompleted, LayerCompleted (derivable)
- Plugin lifecycle events (Dispatched, Cancelled) — unless they affect node state

**Constraints:**
- Journal is append-only. No deletion, no modification.
- Journal is durable — writes survive process restart.
- Journal replay MUST produce identical event sequence (deterministic ordering).
- Journal is scoped to one execution. A new execution creates a new journal.

### 4.7 Snapshot Engine (Mode 3 Only)

```
create(checkpoint_node_id)  → SnapshotId
restore(snapshot_id)        → ExecutionPlan + StatusMap
list()                      → [SnapshotMeta]
validate(snapshot_id)       → bool
```

**Sub-components:**

| Sub-component | Responsibility |
|---------------|---------------|
| **Persist** | Serializes complete runtime image (status_map + scheduler_state + coordinator_state + context) to durable storage |
| **Restore** | Loads snapshot, validates hashes, restores all state, prepares Scheduler for resume at exact wave position |
| **Compatibility Validation** | Checks `execution_plan_hash`, `rir_hash`, `compiler_version`, `execution_mode`, and `schema_version` — any mismatch = SNAPSHOT_INCOMPATIBLE |

**Snapshot schema:**

```yaml
snapshot:
  snapshot_id: "<uuid>"
  created_at: "<iso8601>"
  execution_plan_hash: "<sha256>"       # CEG + execution_plan hash
  rir_hash: "<sha256>"                  # full RIR hash (catches RIR-level changes that don't alter CEG topology)
  compiler_version: "<semver>"          # compiler that produced this RIR (different compiler = potentially different scheduling semantics)
  execution_mode: "3"
  schema_version: "1.0"

  # Complete node status map
  status_map:
    - node_id: "<uuid>"
      status: "SUCCESS" | "FAILURE" | "SKIPPED" | "TERMINATED"
      outputs: {}
      artifacts: []
      evidence: []

  # Scheduler state for exact resume position
  scheduler_state:
    current_layer: <int>
    current_wave: <int>
    completed_nodes: ["<uuid>"]
    ready_queue: ["<uuid>"]
    blocked_nodes: ["<uuid>"]

  # Coordinator state for resume continuity
  coordinator_state:
    runtime_state: "RUNNING"             # always RUNNING in a valid snapshot
    signal_origin: "<node-id>" | null    # which checkpoint node triggered this

  # Context for agent continuity
  context_snapshot:
    session_refs: ["<ref>"]
    memory_refs: ["<ref>"]
    artifact_refs: ["<ref>"]
    variables: {}                         # scoped runtime variables
```

**Restore protocol:**

```
RESTORE(snapshot_id):
  1. LOAD snapshot
   2. VALIDATE (any mismatch = SNAPSHOT_INCOMPATIBLE):
       - snapshot.execution_plan_hash == current_execution_plan.hash
       - snapshot.rir_hash == current_rir_hash
       - snapshot.compiler_version == current_compiler_version
       - snapshot.execution_mode == current_execution_mode
       - snapshot.schema_version is compatible
  3. RESTORE status_map → set all node states
  4. RESTORE scheduler_state → rebuild lane/wave cursor, ready_queue, blocked_nodes
  5. RESTORE coordinator_state → set runtime_state = RUNNING
  6. RESUME execution from next wave
```

**Constraint (RI-014):** Snapshot restore is state restoration, NEVER state re-derivation. The Scheduler does not recompute BLOCKED → READY from scratch on restore — it loads the exact `scheduler_state` from the snapshot.

**Constraints:**
- Snapshot Engine is loaded and active only in Mode 3.
- In Mode 2, any attempt to access Snapshot Engine returns NOT_AVAILABLE.
- Checkpoint nodes in Mode 2 were already rejected at compile time (V-012).
- `execution_plan_hash`, `rir_hash`, `compiler_version`, `execution_mode`, and `schema_version` MUST all match for restore.
- Cross-plan, cross-mode, or cross-version restore is rejected.
- Snapshots are immutable once created. No modification, no deletion outside garbage collection policy (future concern).

### 5.1 Normal Node Lifecycle

```

   │                            │                      │                    │

   │                            │ READY → RUNNING      │                    │

   │                            │ publish(NodeStarted)─────────────────────►│
   │                            │                      │                    │
   │──dispatch(node)──────────────────────────────────►│                    │
   │                            │                      │                    │
   │                            │                 resolve + execute         │
   │                            │                      │                    │
   │◄───ExecutionResult────────────────────────────────│                    │

```


### 5.3 Abort Flow

```
COORDINATOR
     │
     │ abort("INVARIANT_VIOLATION")
     │
     │ runtime_state ← ABORTED
     │
     │ append(Journal, RuntimeAborted(reason))
     │
     │ publish(EventBus, RuntimeAborted)
     │
     │ STOP. No further processing.
     │ (existing plugin processes receive best-effort KILL signals
     │  but their response is not waited for)
```

## 6. Invariants

| ID | Invariant | Enforced By |
|----|-----------|-------------|
| RI-001 | Commit events are immutable once published | Commit Engine |
| RI-002 | Scheduler reacts only to committed events (never invoked directly by Commit Engine) | Commit Engine + Event Bus |
| RI-003 | Every node has exactly one terminal transition | Commit Engine (Duplicate Commit Guard) |
| RI-004 | Status transitions are monotonic (no reversion from terminal) | Commit Engine |
| RI-005 | TERMINATE never propagates — it is absorbing (per ADR-0003-A RT-008) | Coordinator |
| RI-006 | ABORT terminates the entire execution immediately | Coordinator |
| RI-007 | Runtime derives no new graph structure (CEG is immutable) | All components |
| RI-008 | Dispatch never bypasses Commit Engine — every result flows through commit | Coordinator + Dispatcher |
| RI-009 | Commit Engine is the only component allowed to mutate node state | Commit Engine |
| RI-010 | Scheduler decisions are deterministic (same CEG + same status_map → same READY set) | Scheduler |
| RI-011 | Snapshots are Mode-3 only | Snapshot Engine + Pass 3 (V-012) |
| RI-012 | Snapshot is fully self-contained (rehydratable without compiler, graph reconstruction, or external metadata) | Snapshot Engine (Persist) |
| RI-013 | Restore requires hash compatibility (`execution_plan_hash` + `rir_hash` + `execution_mode` + `schema_version` + `compiler_version`) | Snapshot Engine (Compatibility Validation) |
| RI-014 | Restore never re-derives state — it loads exact `scheduler_state` from snapshot | Snapshot Engine |
| RI-015 | Escalation causes clean restart only (terminate → snapshot → reclassify, per F-004) | Coordinator |
| RI-016 | Every visible transition is journaled before publication on Event Bus | Commit Engine + Coordinator |
| RI-017 | Event ordering is deterministic within a single execution; ordering across executions is undefined | Event Bus (Ordered Delivery) |
| RI-018 | Restore reconstructs runtime state only — it never replays side effects (no re-execution) | Snapshot Engine (Restore) |
| RI-019 | Scheduler `runnable_set` remains immutable between committed events within a wave epoch | Scheduler |
| RI-020 | Event publication failure after durable journal write → ABORT with event marked `pending_publication` | Commit Engine |

## 8. Error Handling

### 8.1 Plugin Failure

| Failure Type | Node Result | Plugin State | Runtime Impact |
|-------------|-------------|--------------|----------------|
| Timeout | FAILURE | DEACTIVATE (if 3 in window) | Node marked FAILED, successors evaluated |
| Crash | FAILURE | DEACTIVATE | Node marked FAILED |
| Isolation violation | FAILURE | KILL + DEACTIVATE | Node marked FAILED |
| Result parse error | FAILURE | ACTIVE (retry) | Node marked FAILED |
| Normal failure | FAILURE | ACTIVE | Node marked FAILED |

### 8.2 Internal Failure

| Failure Type | Action |
|-------------|--------|
| Invalid state transition | ABORT_RUNTIME |
| Corrupted journal | ABORT_RUNTIME |
| Double commit attempt | WARNING (idempotent reject) |
| Snapshot checksum mismatch | Reject restore, continue without snapshot |
| Event Bus consumer crash | Disconnect consumer, continue |
| Commit Engine crash during commit | On restart, check journal for partial writes, replay |

### 8.3 Recovery After ABORT

```text
ABORTED runtime:
  1. All plugin processes receive KILL
  2. Journal is flushed and closed
  3. No snapshot is created (runtime integrity unknown)
  4. Audit record written: ABORTED + reason
  5. Manual investigation required before re-execution
```

## 9. Component Boundaries (What Each Component Does NOT Do)

| Component | Does NOT |
|-----------|----------|
| Coordinator | Execute nodes, schedule, validate CEG |
| Scheduler | Mutate CEG, invoke plugins, commit results |
| Dispatcher | Change node state, interpret spec, handle retry logic |
| Commit Engine | Invoke Scheduler, re-derive dependencies, execute plugins |
| Event Bus | Persist events, guarantee delivery, buffer indefinitely |
| Journal | Publish to Event Bus, interpret events, trigger actions |
| Snapshot Engine | Execute nodes, modify CEG, run in Mode 2 |

## 10. Implementation Guidance (Non-Normative)

- **Language:** The Runtime Engine is spec-driven. Implementation language is an engineering choice, not an architectural constraint. Any language that supports process isolation, structured IPC, and deterministic scheduling is sufficient.
- **IPC Mechanism:** Plugin ↔ Core communication via stdout/stdin JSON lines (Mode 2) or Unix domain sockets (Mode 3, for lower latency under high dispatch volume).
- **Journal Backend:** SQLite (single-file, crash-safe, append-only with WAL mode) for v1. Swappable to any append-only store.
- **Snapshot Backend:** Filesystem directory per execution, with manifest.json + immutable blob files per checkpoint. Compatible with git-based storage.
- **Event Bus:** In-process channel/multiproducer-singleconsumer queue for v1. External message broker not required until distributed Mode 3.

## 12. Decision Outcome

The Runtime Engine is defined as a 7-component system (Coordinator, Scheduler, Dispatcher, Commit Engine, Event Bus, Execution Journal, Snapshot Engine) operating over a frozen CEG. Node state and runtime state are orthogonal. The Commit Engine is the single writer of all node state — every transition (READY→RUNNING, RUNNING→SUCCESS/FAILURE, *→TERMINATED, BLOCKED→READY/SKIPPED) flows through it atomically. The Coordinator orchestrates lifecycle but never writes node state directly. All state transitions are journaled before publication (RI-016). The Scheduler and Commit Engine are decoupled via the Event Bus (RI-002). ABORT is a runtime-level integrity response, distinct from node-level TERMINATED (RI-005, RI-006). TERMINATED is absorbing and never propagates. Snapshot restore is pure state restoration from a fully self-contained runtime image, validated against `execution_plan_hash`, `rir_hash`, `compiler_version`, `execution_mode`, and `schema_version` (RI-013, RI-014). Restore never replays side effects (RI-018).

## 13. Consequences

**Positive:**
- Complete audit trail from Router decision through every node transition to terminal state (Journal)
- Scheduler/Commit Engine decoupling enables independent testing and future extension (e.g., custom commit observers)
- ABORT ≠ TERMINATED prevents category errors in failure analysis
- Snapshot self-containment ensures deterministic resume behavior
- Component boundaries are narrow and testable in isolation

**Constraints:**
- Journal adds latency (durable write before event publication) — acceptable tradeoff for auditability
- Single-threaded Commit Engine is a throughput bottleneck (by design — correctness over speed); it is the sole path for all node state transitions including READY→RUNNING and BLOCKED→READY/SKIPPED
- Snapshot restore requires matching `execution_plan_hash`, `rir_hash`, `compiler_version`, `execution_mode`, AND `schema_version` — no cross-version, cross-compiler, cross-plan, or cross-mode resume
- No distributed execution semantics in v1

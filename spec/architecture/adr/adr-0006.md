# ADR-0006 — Execution Consistency & Convergence Controller

**Status:** PROPOSED
**Depends on:** ADR-0004 (Observability Layer), ADR-0005 (Execution State Model), ADR-0003-B (Runtime Engine)
**Layer:** Cross-Cutting — Consistency Verification
**Scope:** All execution modes where traces and/or snapshots exist (Mode 2 partial, Mode 3 full)

---

## 1. Core Thesis

```
The Execution Consistency & Convergence Controller (ECCC)
continuously validates that:

  Trace (what happened) ↔ Snapshot (resume projection) ↔ Replay/Recovery (reconstruction)

remain semantically equivalent within deterministic bounds.

It does NOT execute logic.
It does NOT modify state.
It does NOT enforce policy.
It ONLY detects divergence, classifies drift severity, and emits immutable drift events.

The ECCC is the system's immune layer — it verifies that the
execution substrate has not silently degraded.
```

**Critical boundary — Structural Diff Only:**

```
The ECCC performs STRUCTURAL DIFFERENTIAL COMPARISON only.

It detects:    "X differs from Y at point Z"
It does NOT:   Judge whether the difference is acceptable
It does NOT:   Assign business-impact severity
It does NOT:   Recommend remediation

Severity interpretation and resolution are EXTERNAL concerns
(delegated to Governance, CI verifier, or analysis tools).

The ECCC emits:      raw structural divergence data
External layers:     interpret severity, decide action
```

---

## 2. Problem Statement

ADR-0004 provides a perfect truth layer (immutable traces of everything that happened). ADR-0005 provides a compressed state projection (snapshots for resume). Replay and recovery reconstruct execution from these artifacts.

**But no layer answers:**

```
"Does the snapshot still correctly project the traces?"
"Did the recovered execution match what would have executed?"
"If I replay this execution, will I get the same result?"
"Is the system drifting toward silent inconsistency?"
```

Without the ECCC, drift accumulates silently until:
- A snapshot becomes unrecoverable
- A replay produces different results from the original
- A recovered execution violates dependency closure
- The audit trail contradicts the execution record

## 3. Drift Definition Model

### 3.1 Snapshot Drift (Class A)

```
Snapshot state ≠ valid projection of trace state at snapshot time
```

**Detection criteria:**

| Check | Drift Condition |
|-------|----------------|
| Node status mismatch | `snapshot.status_map[node].status ≠ trace.reconstructed_status[node]` |
| Missing execution record | Node in snapshot.status_map but no trace exists |
| Orphaned status entry | Trace shows node terminal but snapshot has it non-terminal |
| Invalid terminal in snapshot | Snapshot shows SUCCESS but traces show FAILURE for same node |
| Scheduler cursor inconsistency | `snapshot.scheduler_cursor.wave > max_wave_in_traces` |
| Agent state contradiction | Agent summary says tool X succeeded but trace shows tool X failed |

### 3.2 Replay Drift (Class B)

```
Replayed execution trace ≠ original execution trace
```

**Detection criteria:**

| Check | Drift Condition |
|-------|----------------|
| Output hash mismatch | `replay_output_hash ≠ original_output_hash` for identical inputs |
| Tool invocation sequence mismatch | Different tool order or different tools invoked |
| Node execution order change | Replayed wave order ≠ original wave order |
| Lineage divergence | Data flow edges in replay ≠ data flow edges in original |
| Timing divergence (non-critical) | Duration differs (degraded to LOW severity if outputs match) |

### 3.3 Recovery Drift (Class C)

```
Recovered execution ≠ valid continuation of original execution
```

**Detection criteria:**

| Check | Drift Condition |
|-------|----------------|
| Dependency violation | Recovered node executed before its predecessor was committed |
| Missing dependency | Node's predecessor not in snapshot.status_map or trace set |
| Duplicate execution | Node committed twice (original trace + recovered trace both have commit) |
| Wave boundary violation | Recovered execution started at wrong wave |
| Agent continuity break | Inflight agent state in snapshot contradicts last trace before checkpoint |

## 5. Consistency Invariants

| ID | Invariant | Enforced By |
|----|-----------|-------------|
| EC-001 | Trace is the sole authoritative source of execution truth — snapshot is never authoritative | Trace Checker + Snapshot Check |
| EC-002 | Snapshot MUST be derivable from (CEG + traces + scheduler state) via deterministic compression rules (SS-011) | Snapshot Check |
| EC-003 | Replay with identical RIR, compiler, runtime fingerprint, and provider constraints MUST produce identical trace graph | Replay Verifier |
| EC-004 | Recovery MUST preserve completed node outputs, wave boundary correctness, and dependency closure | Snapshot Check + Replay Verifier |
| EC-005 | All drift MUST be explicitly emitted as a DRIFT_EVENT — no silent correction, no hidden repair | Drift Classifier |
| EC-006 | Drift detection is non-intrusive — read-only access to traces, snapshots, and replay outputs | All components |
| EC-007 | Controller never modifies execution state, snapshots, traces, or CEG | All components |
| EC-008 | Controller operates post-facto (after commit) or in parallel (during replay); never on the critical execution path | All components |
| EC-009 | Drift detection is deterministic — same inputs → same divergence class and raw expected/actual data | Drift Differential Engine |
| EC-010 | Drift events are immutable audit artifacts — append-only, never modified | Drift Event Bus |
| EC-011 | Replay drift is ONLY valid when execution was declared deterministic-bounded under ADR-0004 §6.3 constraints; otherwise divergence is classified as UNSPECIFIED_VARIANCE | Replay Verifier |
| EC-012 | Every DRIFT_EVENT MUST include `resolution_contract_ref` (nullable) — a pointer to the external contract (governance, CI, recovery) responsible for resolving this class of drift | Drift Differential Engine |

## 6. Drift Detection Engine

### 6.1 Trace Internal Consistency Check

```
CHECK_TRACE_CONSISTENCY(trace_set, execution_id):
  for each trace in trace_set (ordered by commit.sequence):
    # Gap detection
    if trace.commit.sequence ≠ expected_sequence:
      emit DRIFT(TRACE_GAP, expected, actual)

    # Transition validity
    if not VALID_TRANSITION(trace.previous_status, trace.commit.terminal_status):
      emit DRIFT(INVALID_TRANSITION, trace.node_id)

    # Completeness
    if trace.incomplete AND trace.commit.terminal_status ∈ {SUCCESS, FAILURE}:
      emit DRIFT(INCOMPLETE_TRACE_TERMINAL, trace.node_id)

    # Monotonic sequence
    expected_sequence ← trace.commit.sequence + 1
```

### 6.2 Snapshot vs Trace Projection Check

```
CHECK_SNAPSHOT_PROJECTION(snapshot, trace_set, CEG):
  reconstructed_state ← RECONSTRUCT_STATE(trace_set, CEG)

  for each node in snapshot.status_map:
    # Status match
    if snapshot.status_map[node].status ≠ reconstructed_state[node].status:
      emit DRIFT(SNAPSHOT_STATUS_MISMATCH, node,
                 expected = reconstructed_state[node].status,
                 actual = snapshot.status_map[node].status)

    # Orphan check
    if node ∉ reconstructed_state:
      emit DRIFT(ORPHAN_SNAPSHOT_ENTRY, node)

  for each node in reconstructed_state:
    # Missing check
    if node ∉ snapshot.status_map:
      emit DRIFT(MISSING_SNAPSHOT_ENTRY, node)

  # Scheduler cursor check
  max_trace_wave ← MAX_WAVE(trace_set)
  if snapshot.scheduler_cursor.current_wave > max_trace_wave + 1:
    emit DRIFT(SCHEDULER_CURSOR_AHEAD, expected ≤ max_trace_wave + 1,
               actual = snapshot.scheduler_cursor.current_wave)
```

### 6.3 Replay vs Original Trace Check

```
CHECK_REPLAY_EQUIVALENCE(original_traces, replay_traces):
  # Must have same node count
  if |original_traces| ≠ |replay_traces|:
    emit DRIFT(REPLAY_NODE_COUNT_MISMATCH)

  for each node in original_traces:
    replay_node ← replay_traces[node.id]

    # Output hash match
    if replay_node.outputs.result_hash ≠ node.outputs.result_hash:
      emit DRIFT(REPLAY_OUTPUT_DIVERGENCE, node,
                 expected_hash = node.outputs.result_hash,
                 actual_hash = replay_node.outputs.result_hash)

    # Tool invocation match (for agents)
    if node.node_type = "agent":
      if replay_node.execution.tool_invocations ≠ node.execution.tool_invocations:
        emit DRIFT(REPLAY_TOOL_SEQUENCE_MISMATCH, node)

    # Commit order match
    if replay_node.commit.sequence ≠ node.commit.sequence:
      emit DRIFT(REPLAY_COMMIT_ORDER_MISMATCH, node)
```

## 8. Divergence Classification

### 8.1 Structural Divergence Classes (ECCC)

The ECCC assigns only **structural divergence classes** — raw differential categories.

| Class | Description | Example |
|-------|-------------|---------|
| `STRUCTURAL` | Node status, output hash, or dependency graph differs | Snapshot has SUCCESS, trace has FAILURE |
| `TEMPORAL` | Timing differs but structure matches | Replay duration differs, outputs identical |
| `SEQUENCE` | Order differs but content matches | Tool invocation order changed, same tools |
| `UNSPECIFIED` | Divergence detected but execution was not under deterministic-bounded constraints (EC-011) | LLM provider with temperature > 0 during replay |

### 8.2 Severity Assignment (EXTERNAL)

Severity (LOW / MEDIUM / CRITICAL) is assigned EXTERNALLY by:
- Governance Engine (policy-based severity rules)
- CI/CD pipeline (verification gates)
- Analysis tools (post-facto investigation)

The ECCC emits only the structural divergence class + raw expected/actual data. The external layer maps `divergence_class` + `context` → severity.

### 8.3 Deterministic Divergence Detection

```
DETECT_AND_CLASSIFY(drift_type, expected, actual, context):
  # Determine divergence class
  if drift_type ∈ {STATUS_MISMATCH, OUTPUT_DIVERGENCE, DUPLICATE_EXECUTION}:
    divergence_class ← STRUCTURAL
  else if drift_type ∈ {SEQUENCE_GAP, TOOL_SEQUENCE_MISMATCH}:
    divergence_class ← SEQUENCE
  else if drift_type ∈ {TIMING_DIVERGENCE}:
    divergence_class ← TEMPORAL
  else:
    divergence_class ← UNSPECIFIED

  # If replay and not deterministic-bounded → reclassify
  if drift_type = REPLAY_DRIFT AND context.deterministic_bounded = false:
    divergence_class ← UNSPECIFIED

  return divergence_class
```

## 9. Operational Modes (External Interpretation)

The ECCC operates in a single mode: **structural diff only**. What changes across environments is how external layers interpret the divergence data.

| Environment | External Interpretation |
|-------------|------------------------|
| **Development** | All divergence classes logged; no enforcement; used for debugging |
| **CI/CD** | STRUCTURAL divergence → pipeline failure; TEMPORAL/SEQUENCE → warning |
| **Production Mode 3** | STRUCTURAL divergence → Governance evaluates; snapshot may be invalidated; execution annotated |
| **Forensic Audit** | Full divergence history queried; `resolution_contract_ref` links to remediation decisions |

## 10. Integration Contracts

### 10.1 ECCC ↔ Observability (ADR-0004)

```

### 10.2 ECCC ↔ State Model (ADR-0005)

```
ECCC consumes:   Snapshots for projection validation
ECCC validates:  Snapshot ⇔ Trace consistency (EC-002)

ECCC NEVER:      Modifies snapshots
ECCC NEVER:      Participates in snapshot creation or recovery
```

### 10.3 ECCC ↔ Runtime Engine (ADR-0003-B)

```
ECCC monitors:   Wave transitions via trace sequences
ECCC detects:    Execution divergence, commit order violations

ECCC NEVER:      Blocks execution
ECCC NEVER:      Modifies node state
ECCC NEVER:      Interacts with Commit Engine
```

│                                                      │

│  Structural divergence detection (raw diff only)     │

```

**The loop is closed.** The system records what happened, compresses it for efficiency, reconstructs it for verification, and continuously validates that all representations remain equivalent. No silent drift. No hidden corruption. No unverifiable state.

## 13. Decision Outcome

The Execution Consistency & Convergence Controller is a passive, read-only structural differential verification layer that detects divergence between traces (truth), snapshots (projection), and replay/recovery (reconstruction). It performs structural comparison only — no severity assignment, no policy judgment, no remediation. It emits raw divergence data (class + expected/actual) to an immutable drift event stream. Every drift event carries a `resolution_contract_ref` linking to the external contract responsible for resolution (EC-012). Replay drift is only classified as STRUCTURAL when the execution was declared deterministic-bounded under ADR-0004 §6.3; otherwise it is UNSPECIFIED_VARIANCE (EC-011). Severity interpretation, action decisions, and drift resolution are EXTERNAL concerns delegated to Governance, CI verifiers, and analysis tools.

---

## 14. Consequences

**Positive:**
- System achieves self-verification — silent drift is impossible
- Full auditability of consistency across time (trace events + drift events)
- Replay correctness is formally verifiable, not assumed
- Snapshot validity is continuously checked, not trusted
- Enables formal verification bridge (future ADR-0007)
- Detection is non-intrusive — zero execution path overhead

**Constraints:**
- Verification compute cost scales with trace graph size (O(n²) for full cross-check)
- Drift detection is post-facto — drift may have occurred before detection
- CRITICAL drift requires manual investigation — automatic repair is explicitly excluded
- Requires all three layers (ADR-0004, ADR-0005, ECCC) to be operational
- Mode 2 executions have reduced verification surface (no snapshots to check)

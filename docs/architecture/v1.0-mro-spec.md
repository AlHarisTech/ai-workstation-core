# MCP Release Orchestrator (MRO) — Specification v1.0

**Gateway-Controlled Release Coordination Layer**

## 1. Purpose

The MCP Release Orchestrator (MRO) is a gateway-resident orchestration layer responsible for executing release workflows without modifying underlying MCP tool contracts.

It provides a deterministic bridge between:

- local Git MCP state
- external GitHub API
- release lifecycle coordination

## 2. Design Principles

### 2.1 Non-Intrusive Extension Principle

MRO MUST NOT modify:

- Git MCP capabilities
- GitHub MCP capabilities
- Kernel behavior

It operates strictly as: **an orchestration overlay inside MCP Gateway**

### 2.2 API Isolation Principle

All GitHub operations are executed via direct API bridge, not MCP abstraction.

### 2.3 Fail-Closed Release Principle

Any incomplete release step results in:

- no tag publication
- no GitHub release creation
- no external state mutation

### 2.4 Deterministic Execution Principle

Given identical input state:

- same tag name
- same commit hash
- same repository context

MRO produces identical release outcome.

## 4. Execution Pipeline

### 4.1 Phase 1 — Local State Capture

Executed via Git MCP:

- commit current state
- retrieve commit hash
- verify clean working tree

**Output:** `commit_sha`

### 4.2 Phase 2 — Tag Construction (Local Only)

MRO generates:

- version tag (e.g. v1.0.0)
- associates with commit_sha

No remote operation yet.

### 4.3 Phase 3 — GitHub Authentication

Uses:

- `GITHUB_TOKEN` ONLY
- no SSH
- no git remote credentials

**Validation:**
- token presence
- repository access verification

### 4.4 Phase 4 — GitHub Tag Publication (API Bridge)

MRO performs:

- create git tag reference via GitHub API
- bind tag → commit_sha

### 4.5 Phase 5 — Release Creation

MRO creates GitHub Release:

**Includes:**
- tag version
- architecture documents
- commit reference
- optional release notes payload

### 4.6 Phase 6 — Finalization
- emit trace event (ReleaseEvent)
- update observability layer
- mark release status = SUCCESS

## 5. Failure Model

### 5.1 Partial Failure Rule

If any step fails:

| Step | Action |
|---|---|
| Tag creation fails | abort entire release |
| Release creation fails | rollback tag reference (logical) |
| Auth failure | immediate termination |
| Git MCP failure | abort before orchestration |

### 5.2 Failure States

- `AUTH_INVALID`
- `GIT_STATE_INVALID`
- `TAG_CREATION_FAILED`
- `RELEASE_CREATION_FAILED`
- `NETWORK_FAILURE`

All map to: `RELEASE_ABORTED` (no external side effects beyond initial step)

## 8. Integration Point

MRO MUST be invoked:

- after Git MCP commit stage
- before response finalization

Pipeline position:

```
Git MCP Commit → MRO → GitHub API → Trace Finalization
```

## 9. Security Model

### 9.1 Secrets Handling
- `GITHUB_TOKEN` is ephemeral
- never stored in trace logs
- never propagated to MCP tools

### 9.2 Boundary Rule

MRO is the only component allowed to call external GitHub APIs.

## 10. Determinism Guarantees

MRO guarantees:

- same commit → same tag
- same version input → same release structure
- no timing-dependent variation in outputs

## 11. Observability Integration

MRO emits:

- `ReleaseStartEvent`
- `TagCreationEvent`
- `ReleasePublishEvent`
- `ReleaseFailureEvent`

All linked to: TraceGraph in MCP Gateway

|---|---|

| GitHub MCP | Not used for release path |
| MCP Gateway | Control plane |

# MCP Release Finalization Layer (RFL)

**Version:** 1.0 — Crash-Safe Deterministic Release Closure Layer

## 1. Persistent Queue Recovery Model

### 1.1 Purpose

This model defines how MCP Gateway reconstructs release state after:

- system restart
- crash recovery
- process interruption
- partial execution failure

### 1.2 Design Principle

Queue state is the source of truth, not runtime memory.

All release operations MUST be recoverable from persisted state.

### 1.3 Queue Persistence Structure

Each queued release entry MUST include:

- release_id
- commit_sha
- version_tag
- status (PENDING_EXTERNAL | RETRYING | FAILED | COMPLETED)
- retry_count
- next_retry_at
- last_error
- idempotency_key
- created_at
- updated_at

### 1.4 Recovery Procedure (On Startup)

Upon gateway initialization:

**Step 1** — Load persisted queue
- read all release entries from storage layer

**Step 2** — Rehydrate state machine
- reconstruct in-memory queue from persisted state
- restore retry counters and scheduling metadata

**Step 3** — Resume execution deterministically
- process only entries with:
  - status = PENDING_EXTERNAL OR RETRYING

### 1.5 Recovery Constraint
- NO re-generation of release payload
- NO recomputation of commit state
- NO re-validation of already validated entries

## 2. Idempotency Contract

### 2.1 Purpose

Guarantees that repeated execution attempts NEVER create duplicate GitHub releases or tags.

### 2.2 Idempotency Key Definition

Each release MUST compute:

```
idempotency_key = SHA256(commit_sha + ":" + version_tag)
```

### 2.3 Enforcement Rule

Before any external operation:

- check if idempotency_key exists in completed store
- if exists → skip execution
- if not → proceed

### 2.4 GitHub Deduplication Strategy

All GitHub operations MUST be guarded by:

- tag existence check
- release existence check

If either exists:
- treat operation as SUCCESS (idempotent acceptance)

### 2.5 Idempotent State Mapping

| State | Behavior |
|---|---|
| NOT_EXISTS | execute release |
| PARTIAL_EXISTS | reconcile + mark complete |
| FULL_EXISTS | skip execution |

## 3. Replay Determinism Rule

### 3.1 Purpose

Ensures that system replay after crash produces identical results.

### 3.2 Deterministic Input Set

Replay MUST depend ONLY on:

- commit_sha
- version_tag
- repository context
- persisted queue state
- idempotency_key

### 3.3 Deterministic Output Guarantee

Given identical state:

The system SHALL produce identical:

- release artifact
- GitHub tag
- release metadata
- observability trace

### 3.4 No Side-Effect Divergence Rule

During replay:

- NO additional GitHub releases are created
- NO duplicate tags are pushed
- NO variation in retry scheduling
- NO state mutation outside controlled transitions

### 3.5 Replay Execution Model

```
Load persisted queue
  ↓
Sort by deterministic order (release_id)
  ↓
Check idempotency key
  ↓
Execute missing external operations only
  ↓
Update state machine
  ↓
Persist final state
```

## 4. System Guarantees

### 4.1 Hard Guarantees
- crash-safe queue recovery
- idempotent release execution
- deterministic replay behavior
- no duplicate external side effects

### 4.2 Failure Isolation Guarantees
- external API failure does NOT corrupt queue state
- partial execution is safely resumable
- retry does NOT mutate idempotency identity

### 4.3 Consistency Model

The system operates under:

**Eventual External Consistency with Internal Strong Consistency**

- internal state = strongly consistent
- GitHub state = eventually consistent

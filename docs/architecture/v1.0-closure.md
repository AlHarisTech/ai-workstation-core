# MCP Gateway — Runtime Closure Pack

**Version:** 1.0 — Formal System Finalization Layer

## 1. State Machine Specification

### 1.1 System States

The MCP Gateway execution lifecycle is defined as a deterministic finite state machine:

```
INIT
  ↓
VALIDATED
  ↓
ROUTED
  ↓
EXECUTING
  ↓
RESPONDING
  ↓
CLOSED
```

### 1.2 State Definitions

#### INIT

Request has been received but not yet validated.

- No kernel evaluation performed
- No routing allowed

#### VALIDATED

Session and policy validation completed successfully.

- Fail-closed enforcement passed
- Backpressure eligibility confirmed

#### ROUTED

Deterministic routing decision completed.

- Target tool selected
- Adapter chain resolved

#### EXECUTING

Tool adapter execution in progress.

- Circuit breaker applied
- Retry budget active

#### RESPONDING

Execution completed and response being assembled.

- Trace aggregation in progress
- Telemetry emission allowed

#### CLOSED

Final terminal state.

- Response returned
- Trace finalized
- Session step complete

### 1.3 Failure Transitions

Any state MAY transition to failure termination paths:

```
ANY_STATE
  ↓
FAILED
  ↓
CLOSED
```

Failure triggers:
- session invalidation
- policy rejection (kernel)
- circuit breaker OPEN state
- retry budget exhausted
- timeout violation
- backpressure rejection

### 1.4 Abort Paths (Hard Stop Conditions)

Abort overrides normal lifecycle:

- invalid request envelope
- security/session violation
- kernel fail-closed trigger

**Result:** Immediate transition → CLOSED (no routing, no execution)

## 2. Failure Taxonomy Matrix

### 2.1 Classification Table

| Failure Type | Layer | Handler | Mitigation | Observability Event |
|---|---|---|---|---|
| Invalid Session | Gateway | SessionValidator | Reject immediately | SessionRejectEvent |
| Policy Violation | Kernel | KernelEngine | Fail-closed | PolicyRejectEvent |
| Saturation | Gateway | BackpressureController | Soft reject | SaturationEvent |
| Routing Failure | Router | DeterministicRouter | Fallback route | RoutingFailureEvent |
| Tool Timeout | Adapter | TimeoutAdapter | Retry (budgeted) | TimeoutEvent |
| Tool Crash | Adapter | CircuitBreaker | Open circuit | CircuitOpenEvent |
| Retry Exhaustion | Gateway | RetryBudgetController | Stop execution | RetryExhaustedEvent |
| Latency Overflow | Gateway | LatencyGuard | Abort request | LatencyViolationEvent |
| Resource Exhaustion | Runtime | SessionTracker | Evict session | SessionEvictionEvent |

### 2.2 Failure Propagation Rule

Failures SHALL NOT propagate upward across layers.

Each layer:
- handles locally
- emits observability event
- returns bounded failure response

### 2.3 Recovery Policy

| Failure Class | Recovery Allowed |
|---|---|
| Transient Tool Failure | Yes (retry budget) |
| Routing Failure | Yes (deterministic fallback) |
| Circuit OPEN | Yes (HALF-OPEN probing) |
| Kernel Policy Failure | No (terminal) |
| Session Invalid | No (terminal) |

## 3. Contract Compatibility Rules

### 3.1 Versioning Model

The system uses strict semantic layering:

- Kernel Version: Immutable (v0.6.2 frozen)
- Gateway Version: incremental (v1.0 → v1.4+)
- Adapter Version: independent per tool

### 3.2 Kernel Immutability Rule

The kernel:

- MUST NOT be modified after freeze (v0.6.2)
- MUST NOT be extended with execution logic
- MUST NOT participate in routing decisions

Kernel role is strictly: **Policy Evaluation + Audit Only**

### 3.3 Adapter Compatibility Contract

All adapters MUST:
- implement standard execution interface
- support timeout + retry wrapping
- support circuit breaker integration
- emit standardized observability events

**Compatibility Rule:** Any adapter MUST be replaceable without modifying Gateway core logic.

### 3.4 Routing Compatibility Rule

Routing logic MUST:
- remain deterministic across all versions
- not depend on runtime system state outside defined context
- preserve identical input → identical output guarantee

### 3.5 Backward Compatibility Rule

Gateway upgrades MUST ensure:
- existing MCPRequest schema remains valid
- MCPResponse schema remains stable
- trace format remains reconstructable

### 3.6 Forward Compatibility Rule

Future extensions MUST:
- not alter execution semantics of existing flows
- only extend via:
  - new adapters
  - new observability signals
  - new optional middleware layers

### 3.7 Breaking Change Policy

A change is considered breaking if it affects:
- routing determinism
- kernel evaluation output
- execution order
- failure handling semantics

Such changes require: **full version bump + contract revision**

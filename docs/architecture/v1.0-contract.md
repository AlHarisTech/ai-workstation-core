# MCP Gateway Production Engineering Spec (Auditable Version)

**Version:** 1.0 — Final Production Contract Document

## 1. Purpose

This document defines the production engineering contract for MCP Gateway as a deterministic execution system that mediates requests between orchestration layers and tool execution systems.

It specifies behavioral guarantees, bounded constraints, and system contracts suitable for audit, review, and production deployment validation.

## 2. System Scope

MCP Gateway operates as a control gateway between:

- OpenCode (orchestration layer)
- MCP Tools (Filesystem / Git / GitHub)
- Kernel Policy Engine (v0.6.2 frozen)

The system enforces:

- deterministic routing
- fail-closed validation
- bounded execution
- controlled failure propagation
- non-invasive observability

## 3. Architecture Overview

```
OpenCode
  ↓
Session Validation (Fail-Closed)
  ↓
Backpressure Controller
  ↓
Kernel Policy Engine (v0.6.2 - Frozen)
  ↓

  ↓
Circuit Breaker Layer
  ↓
Retry Budget Controller
  ↓
Tool Adapters (Filesystem / Git / GitHub)
  ↓
Execution Layer
  ↓
Response + Trace + Telemetry Snapshot
```

## 4. Design Constraints

### 4.1 Deterministic Execution Constraint

Routing decisions are defined as deterministic transformations of request inputs under identical system state.

- Time-based randomness is not part of routing logic
- Race conditions are mitigated at contract level
- Routing behavior is defined by static resolution rules

### 4.2 Fail-Closed Constraint

Any invalid state results in immediate termination of request processing prior to routing.

Triggers include:

- invalid session
- policy rejection
- malformed request envelope

### 4.3 Bounded Resource Constraint

System execution is bounded by explicit limits:

- memory per request
- latency per request
- session count
- retry budget per request

### 4.4 Failure Isolation Constraint

Failures in tool execution are isolated using circuit breaker semantics and must not propagate to gateway or router layers.

### 4.5 Observability Constraint

Observability is strictly non-invasive:

- does not modify execution behavior
- does not influence routing decisions
- operates via sampling where applicable

## 5. Kernel Contract (v0.6.2 — Frozen)

The kernel is defined as a policy-only enforcement engine.

**Responsibilities:**
- request validation
- policy evaluation
- audit event generation

**Constraints:**
- no routing logic
- no execution logic
- no extensibility beyond frozen version

## 6. Execution Pipeline Contract

The system SHALL execute requests in the following logical order:

1. Session Validation (fail-closed)
2. Backpressure Evaluation
3. Kernel Policy Evaluation (audit path)
4. Deterministic Routing Decision
5. Circuit Breaker Evaluation
6. Retry Budget Enforcement
7. Tool Adapter Execution
8. Response Construction
9. Trace Aggregation
10. Telemetry Emission

## 7. Backpressure Contract

The system SHALL enforce:

- per-session queue limits
- global saturation thresholds
- tool-level throttling
- pre-execution rejection under saturation conditions

The system SHALL NOT:

- allow uncontrolled queue growth
- defer saturation handling to downstream components

## 8. Circuit Breaker Contract

Each tool adapter MUST implement:

- CLOSED state (normal execution)
- HALF-OPEN state (recovery probe)
- OPEN state (failure isolation)

Transition conditions SHALL be based on:

- failure frequency
- latency deviation
- saturation signals

## 9. Retry Budget Contract

Retry behavior SHALL be governed by:

- global retry budget per request
- per-tool retry limits
- exponential backoff with jitter

The system SHALL prevent:

- retry amplification loops
- uncontrolled retry storms

## 10. Routing Contract

Routing MUST be:

- deterministic under identical inputs
- independent of wall-clock time
- free of non-deterministic selection logic

Routing output SHALL depend only on:

- request payload
- session context
- kernel policy result
- static routing rules

## 11. Tool Adapter Contract

All tool adapters MUST:

- normalize execution interface
- enforce timeout boundaries
- enforce retry + circuit breaker policies
- emit execution events to observability layer

Supported adapters:

- Filesystem MCP
- Git MCP
- GitHub MCP

## 12. Observability Contract

### 12.1 Trace Model

Each request SHALL produce a TraceGraph containing:

- ordered execution events
- tool invocation boundaries
- routing decisions
- failure events

Trace size is explicitly bounded per request.

### 12.2 Telemetry Model

Telemetry SHALL include:

- latency distributions
- queue depth metrics
- circuit breaker state counts
- retry budget consumption

Telemetry MAY be sampled.

### 12.3 Control Signals (Passive)

System MAY emit signals:

- saturation_warning
- routing_pressure_high
- retry_budget_depletion_risk
- tool_health_degradation

These signals MUST NOT influence execution flow.

### 12.4 Health Scoring Model

Health scores SHALL be deterministic functions of observed metrics:

- Tool Health Score
- Router Stability Score
- Gateway Load Score
- System Saturation Index

No learning or adaptive mechanisms are permitted.

## 13. Production Efficiency Contract (v1.4)

### 13.1 Memory Constraints
- TraceGraph is bounded per request
- ring-buffer telemetry is enforced
- session tracking is capped

### 13.2 Latency Constraints
- hard request latency ceiling applies
- fast-path execution MAY skip non-critical tracing

### 13.3 Session Lifecycle Constraints
- maximum session limit enforced
- idle session eviction applied
- heartbeat-based lifecycle management used

### 13.4 Kernel Signal Usage

Kernel signals are READ-ONLY.

They MAY be used for observation only and MUST NOT affect control logic.

## 14. Failure Model Contract

The system SHALL handle:

- partial tool failure
- timeout cascading
- retry amplification
- routing saturation
- session exhaustion

Mitigation mechanisms:

- circuit breakers
- retry budgets
- backpressure enforcement
- deterministic routing rules

## 15. System Guarantees (Formalized)

### 15.1 Hard Guarantees
- fail-closed session validation
- deterministic routing contract
- bounded memory usage per request
- bounded latency per request
- circuit breaker isolation enforcement

### 15.2 Conditional Guarantees
- observability completeness under sampling
- stable performance under defined load envelopes

## 16. Production Readiness Statement

The MCP Gateway system is defined as:

A deterministic, bounded execution control gateway with enforced failure isolation and non-invasive observability suitable for production workloads under defined constraints.

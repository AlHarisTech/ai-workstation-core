# MCP Release Orchestrator (MRO) — Pending State Protocol

**Version:** 1.0 — External Dependency Degradation Handling Layer

## 1. Purpose

This protocol defines the system behavior when the MCP Release Orchestrator (MRO) enters a state where external dependencies (e.g., GitHub API, authentication layer, network availability) are unavailable.

It ensures:

- deterministic behavior under failure
- no retry amplification
- no uncontrolled external pressure
- safe queued release execution

## 2. Scope of External Dependencies

MRO external dependencies include:

- GitHub API (tag/release creation)
- Authentication provider (GITHUB_TOKEN)
- Network connectivity to GitHub endpoints

Any failure in these systems triggers Pending State Mode.

## 3. MRO Execution States

### 3.1 Normal Flow

```
VALIDATED → TAGGED → PUBLISHED → COMPLETED
```

### 3.2 Pending Flow (External Dependency Failure)

```
VALIDATED → TAGGED → PENDING_EXTERNAL → QUEUED → COMPLETED
```

### 3.3 Failure Flow (Terminal Abort)

```
ANY_STATE → FAILED → CLOSED
```

## 4. Pending State Definition

### PENDING_EXTERNAL

System enters this state when:

- GITHUB_TOKEN is missing or invalid
- GitHub API unreachable
- network timeout occurs during publish stage
- rate limiting blocks external calls

**Behavior in this state:**
- no retry loops initiated immediately
- release payload is persisted locally
- execution is suspended, not failed
- system emits observability event only

## 5. Retry Strategy (Anti-Retry Storm Design)

### 5.1 Core Principle

**Retry MUST be decoupled from execution flow**

No inline retry loops are allowed inside MRO execution path.

### 5.2 Retry Policy Model

Retries are governed by:

- exponential backoff (bounded)
- global retry window (not per request loop)
- jitter injection for distributed stability
- max retry attempts cap

### 5.3 Retry States

| State | Behavior |
|---|---|
| INITIAL FAILURE | enter PENDING_EXTERNAL |
| BACKOFF PHASE | wait scheduled retry window |
| RETRY ATTEMPT | revalidate external dependency |
| SUCCESS | resume pipeline |
| FINAL FAILURE | mark as FAILED |

### 5.4 Anti-Storm Constraint

The system SHALL guarantee:

- no parallel retry execution per release
- no recursive retry calls
- no uncontrolled retry fan-out

## 6. Queued Release Model

### 6.1 Definition

A queued release is a fully prepared release object awaiting external publication.

### 6.2 Queue Structure

```
ReleaseQueue:
  - release_id
  - commit_sha
  - tag
  - payload
  - status = PENDING_EXTERNAL
  - retry_state
  - next_retry_at
```

### 6.3 Queue Behavior
- FIFO ordering per repository
- deterministic replay of release attempts
- no duplicate release creation
- idempotent execution guaranteed

### 6.4 Queue Processing Rules
- Only one active release attempt per repo
- Next execution only after previous completion
- Queue is state-driven, not time-driven

## 7. Deterministic Retry Scheduling

Retry timing is computed using:

- fixed backoff curve
- bounded jitter factor
- deterministic seed based on:
  - commit_sha
  - version tag

**Result:** Same input → same retry schedule

## 8. Observability Events

MRO MUST emit the following events:

### 8.1 Pending Events
- `ReleasePendingExternalEvent`
- `ReleaseQueuedEvent`
- `ReleaseRetryScheduledEvent`

### 8.2 Recovery Events
- `ReleaseExternalRecoveredEvent`
- `ReleasePublishedEvent`

### 8.3 Failure Events
- `ReleaseFinalFailureEvent`
- `ReleaseAbortEvent`

## 9. Failure Semantics

### 9.1 External Failure ≠ System Failure

External dependency failure:

- DOES NOT fail the system
- DOES NOT abort local pipeline
- DOES NOT rollback prepared state

### 9.2 Terminal Conditions

Only these conditions terminate execution:

- invalid release definition
- corrupted local state
- kernel policy violation
- explicit abort signal

## 10. State Persistence Contract

When entering pending state, system MUST persist:

- release payload
- commit reference
- retry schedule
- failure reason

This ensures: **full replayability without recomputation**

## 11. System Guarantees

### Hard Guarantees
- no retry storms
- no duplicate releases
- deterministic retry scheduling
- idempotent release execution
- no external dependency blocking of internal system

### Soft Guarantees
- eventual consistency with GitHub
- eventual release publication under retry window
- stable queue progression under degraded network

## 12. Integration Point in MCP Gateway

```
Git MCP Commit
  ↓
MRO Execution
  ↓
IF external available → publish
ELSE → PENDING_EXTERNAL
  ↓
Queue Processor (async)
  ↓
GitHub API Bridge
```
